# 生产摄像机首帧速度专项调研

## 1. 结论与边界

样本通道 `34020000001320000030` 有值得验证的优化空间，优先调查媒体就绪之后的播放器准备、资源加载和媒体连接。现有证据不足以承诺固定秒数的收益。

- 六次新建媒体就绪样本中，五次在 616–760ms，另一次为 1833ms。
- 五次新建媒体且收到首帧反馈的样本，请求收到至反馈为 2441–10142ms。
- 最新慢样本媒体 689ms 就绪、691ms 发出播放地址，10142ms 收到首帧反馈；媒体就绪至反馈相隔 9453ms。
- 当前首帧反馈是读取到有效视频尺寸的代理指标，不等于真实屏幕首帧；服务端收到反馈的时间还包含上报传输。
- 已完成生产记录与本地源码关联分析，尚未完成受控浏览器实测或优化前后对照。

本轮只读检查生产日志、文件和数据库；SQLite 通过 Python sqlite3 的 `mode=ro` 与 `query_only` 查询。未修改生产配置、业务数据或程序，未重启、部署。日志中的播放为生产自然发生记录，本次没有主动发起摄像机点播。

### INVITE 失败链路

18:07:22 样本 Call-ID 为 `uac-1792404442024361240`。SIP trace 只见 INVITE 发出与重传，没有 100/200。接口约 10 秒返回超时后仍可见重传；reason_code 为 media_timeout，但消息明确为等待 INVITE 应答超时。

本地代码能解释该行为：`uac/invite_outcome.go:177` 用 goroutine/select 保证接口总超时，超时后 Close；`server/third_party/sipgo/dialog_client.go:220` 的 Close 不发送 CANCEL，也不终止事务；WaitAnswer 在 ctx 取消后走 inviteCancel，无临时响应时继续等待响应或事务结束（:398）。因此接口等待边界与 SIP 事务生命周期不同。

这与生产现象一致，但生产二进制与本地精确对应尚未验证。后续需核对 SIP 定时器、晚到响应和资源回收，不能把无临时响应时不发 CANCEL 本身判为协议错误，也不能直接强制终止所有事务。该问题影响失败恢复，不能解释成功媒体已就绪后的慢首帧。

## 6. 下一阶段需求范围（供确认，尚未实施）

目标：用真实可见首帧衡量同一通道的用户等待时间，减少可证实的串行等待与重复加载，并保持成功率、切换正确性与兼容性。

用户故事：用户打开或切换此摄像机时，能尽快看到首帧，并准确区分媒体建立、播放器加载、已呈现和失败。

建议先后顺序：

1. 明确并补齐点击至真实首帧的计量，记录协议、解码路径、资源与连接阶段；修正状态语义和统计口径。
2. 基于瀑布证据评估 EasyPlayer 资源版本缓存、必要资源预取，以及播放器准备与点播并行；保留旧会话释放和异步代次隔离。
3. 对比同一通道的 WSS-FLV、HTTPS-FLV、WebRTC；受控比较音频开启/关闭。只有确认实际选中路径后才讨论收益。
4. 独立处理 INVITE 超时分类与事务收尾；最后根据关键帧证据评估 GOP 与 ZLM 参数。

非目标：本轮不升级播放器、不整体改播放架构、不强制更换所有协议、不改摄像机码率/GOP、不发布生产。

验收口径：

| 场景 | 输入/操作 | 需要的证据与期望 |
| --- | --- | --- |
| 冷/热静态资源 × 冷/热媒体 | 同一通道、浏览器与网络，分别首次播放和重复播放 | 各组记录点击、API、资源、连接、首媒体字节、真实首帧；至少 20 次有效样本作为初步基线，尾延迟需更大样本 |
| 协议与音频对照 | 单变量切换协议或音频 | 确认实际协议/解码器；比较首帧 p50/p95、失败率、卡顿，不能把代理反馈改善当作真实改善 |
| 会话切换 | A→B→A、关闭后快速重开、失败后重试 | 无旧首帧归入新会话、无误停新流、无重复播放器占用 |
| 首帧与状态 | 媒体先就绪、前端仍未呈现 | 不提前宣称已呈现；真实渲染事件/帧回调与必要的录屏对齐，WASM/canvas 路径单独验证 |
| 无应答与晚到响应 | 测试环境模拟无 1xx、晚到 1xx/2xx | API 按时结束，事务与资源最终按策略回收；不在客户生产注入故障 |

量化收益目标应在完整基线后确定。初步样本不足以给出可靠全量 p95，也不能承诺秒开。上述内容是下一阶段范围建议，不代表已完成实现或生产验收。
