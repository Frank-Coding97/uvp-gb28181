# 结论

增量协议显著减小响应体，但当前每轮仍完整查库、构树和计算差异。1 万设备的全展开目录会产生约 12 万 DOM 节点，首屏和再次展开已有明显主线程阻塞。老板确认常见规模远低于 1 万台，当前暂不安排虚拟滚动、Redis 缓存或后端构树优化；达到实际设备规模或出现可复现卡顿后再复测决定。

# 测试环境与范围

- 日期：2026-10-12；本机 Apple M5，32 GiB 内存、10 逻辑 CPU；macOS-26.5-arm64-arm-64bit-Mach-O。
- 平台 Worktree：device-channel-tree；本轮仅新增测试、测试工具和报告，未修改产品实现。
- 后端：临时 SQLite WAL 库，1 个部门、3 层行政区、每台设备 1 个通道，初始在线/离线各半；测综合目录 national。测试结束自动删除临时数据库。
- 通过真实 Gin 目录控制器和 GORM 查询执行请求；未经过 TCP、登录中间件、VPN 或 MySQL，因此不是当前远端 MySQL 的容量结论。
- 全量 1 次，无变化 5 次，1% 状态反转 3 次，每个筛选 3 次。样本少，P95 只用来发现瓶颈，不作为正式容量承诺。
- 并发为同时启动的页面刷新波次，共 2 轮，下一轮不早于 10 秒，上一轮未完成不叠加。同一轮请求共享当前范围，但逐轮更新已确认的 revision。
- 仅目录请求参与并发，未混入右侧列表、统计和其它业务请求；仍需专用环境长时间整页压测。
- 浏览器为独立 Chromium 上的真实 DirectoryPanel 组件，API 使用临时合成响应；测量不包含网络传输、模块下载或完整登录页面。容器 320×760，默认全部展开。

# 后端结果

| 设备数 | 首次全量 | 全量字节 | 无变化 P50 / P95 | 无变化响应 | 1% 状态变化 P50 / 响应 |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 42.2 ms | 265,927 B | 37.9 / 41.7 ms | 183 B | 38.3 ms / 3,029 B |
| 10,000 | 666.3 ms | 2,673,435 B | 505.0 / 521.8 ms | 183 B | 508.1 ms / 28,816 B |
| 50,000 | 2439.2 ms | 13,453,438 B | 2589.9 / 4732.8 ms | 183 B | 1526.9 ms / 144,216 B |

- 无变化请求仍为 **7 次 SQL**，读取行数分别为 **2,004 / 20,004 / 100,004**。
- 有关键词/状态筛选时先构完整树再裁剪；5 万设备搜索只返回少量资源，中位仍为约 2.22–2.35 秒，读取约 10 万行。
- 1% 变化请求包含本地造数状态更新，因此其 SQL 次数/读写行数多计了 1 次更新；响应耗时本身从请求进入控制器开始计时，不包含造数更新。
- 最新版本号逐轮传递后，已测状态变化请求全部为增量，无异常全量 reset。

|---:|---:|---:|---:|

# 浏览器结果

| 设备数 | 展开行 / DOM 总节点 | 首次渲染 | 无变化同步 | 单节点状态变化 | 再次展开 | 树内搜索 |
|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 1,003 / 12,094 | 308.9 ms | 34.2 ms | 31.4 ms | 217.1 ms | 37.5 ms |
| 10,000 | 10,003 / 120,094 | 2180.2 ms | 17.8 ms | 350.5 ms | 1601.1 ms | 164.9 ms |

- 两档浏览器场景均无 JS 错误；无变化同步前后滚动位置保持。
- 1 万设备最大观测主线程长任务约 1.64 秒；30 帧连续滚动采样没有 >50ms 的帧，但不能据此否认展开/状态更新时的卡顿。
- 1 万场景结束时 Chrome 报告 JS 堆约 587 MB；这是多次展开/搜索后的瞬时估算，未强制 GC，不作为稳定常驻内存。
- **5 万设备全展开浏览器测试未执行**：已有 1 万场景的 DOM 和堆压力证据，按比例可能达约 60 万 DOM 节点。为保护当前交互工作机停止升档；此推算不是实测。
- 每个浏览器规模只跑一次，计时含等待绘制帧，属于渲染基线而非统计性 P95。

# VPN 只读基线

- 使用项目当前 MySQL 配置，仅执行 11 次 SELECT 1；MCP 账号访问被拒绝后采用显式 opt-in 的 Go 只读探针，未执行任何远端写入。
- 建连加首次查询：**445.8 ms**；复用同一连接 10 次查询，样本 P50 **105.6 ms**，最大 **233.5 ms**。
- 该数据包含驱动和数据库应答时间，不是纯网络 RTT，不包含 MCP 工具调用耗时。
- 若当前目录请求串行执行 7 次类似往返，按本次 P50 粗估仅往返就可能贡献约 0.74 秒，此外还有读取结果传输和执行时间。这只是量级说明，不能直接与 SQLite 耗时相加推导公网容量。
- VPN 的路由、抖动、带宽、丢包和连接配置均有区别，因此本次结果不能宣称等同所有公网环境。

# 当前决策

老板确认常见设备规模远低于 1 万台，因此本次压测仅作为基线，暂不继续做虚拟滚动、懒加载、Redis 缓存或后端构树优化。只有当真实设备规模接近当前压测高位，或用户遇到可复现的响应/渲染卡顿时，再按相同基线复测并决定是否优化。

# 复现

在本 Worktree 的 server 目录执行：

```sh
UVP_DIRECTORY_LOAD=1 UVP_DIRECTORY_LOAD_OUTPUT=/tmp/uvp-directory-load-20261012 go test ./app/gb28181/controllers -run "^TestDirectoryLoad$" -count=1 -timeout=20m -v
```

可用 UVP_DIRECTORY_LOAD_SIZES=1000,10000 指定规模；未设置显式启用变量时测试自动跳过。VPN 探针与上述隔离造数逻辑分别受独立开关控制，勿对公共环境运行任意压力测试。

浏览器驱动依赖本 Worktree 的 Vite 5189，以及只绑定 loopback 的临时 fixture HTTP 18991。将 browser-harness.html、browser-driver.js 和生成的 tree-N.json 放在临时 fixture 目录，启动只读静态服务器；通过 Playwright 的 page.request 获取 browser-driver.js 并调用函数 (page, N)。每次创建独立 browser context，结束自动关闭。生产页面和认证状态不被修改。

原始结果见同目录 backend.json、vpn.json、browser-1000.json 和 browser-10000.json；数据文件只含合成资源和性能数值。
