## ⚠️ v2.1 → v3 修订说明（先读这段，它决定全文怎么用）

**触发**：澄清需求原意。

原话：「我刚才说对外提供接口的意思，是**先紧着我们自己的平台来**。对外提供接口的时候，
**可以参考这个接口直接对外提供，就不用再去设计了**，还是走以前对外提供的那种方式。」

⇒ 需求是**两件事、两个时间点**：

| | 现在（本次设计范围） | 将来（不在本次范围） |
|---|---|---|
| 做什么 | 把内部这套服务配置接口重做 | 在**既有对外栈**里另写一套对外接口 |
| 约束 | 内部最优（原子性 / 一次落盘 / 无特例） | 服从 `api/openapi-v1.yaml` 既有风格 |
| 关系 | —— | **参考本方案的资源模型**（字段、分组、命名、语义），不重新设计 |

### ⛔ v2.1 错在哪：我把"参考"读成了"共用"

| | v2.1 的错误理解 | v3 的正确理解 |
|---|---|---|
| 模型 | 一份业务层 + 两个薄适配器，**同一个接口同时服务内外** | 内部一套、对外一套，**两套实现、一套资源模型** |
| 对现有的影响 | 要求重构对外栈、让对外薄包装内部 service | **不动对外栈**，对外保持它现在的独立形态 |
| 内部路径命名 | 跟对外对齐到 `/configs/service`（为对外改名） | **`/api/gb28181/service-config`** —— 改名理由是内部命名本身不对（去 `sip`），与对外无关，见 §2.0 |
| 前置阻塞项 | 「必须先泛化对外网关才能发布」 | 与本次无关，是**将来对外时**的事 |

⛔ 最重要的一条更正：**"对外发布 = `public.go` 加 2 行"是我说错的。**
对外栈是一整套独立实现，加一个对外能力 ≠ 加 2 行（见 §7 的实测清单）。

## 0. 设计前提（v3 三条）

| # | 约束 | 事实来源 | 对设计的影响 |
|---|---|---|---|
| 1 | **本次只面向平台自身**（内部管理端） | 需求原意（见上） | 不受对外契约约束 ⇒ 可以按内部最优设计。**但仍要"规整"**：规整的代价是零，将来对外照参考才薄 |
| 2 | 存储是**一个 yml 文件**，不是关系库 | `server/config/config.yml`；`ymlconfig.SaveConfig()` 全量重写 | 「事务」只能靠「**一次写盘 + 内存整体回滚**」，不能靠 DB 事务 |
| 3 | 部署形态**单进程**（含 Windows 单机版） | 交付形态 | 不需要分布式一致性；进程内锁 + 乐观锁足够 |

> 「将来对外要参考」在本次设计里只体面为一句话：**资源模型要规整**。
> 具体是四条：① 路径收敛到一条 ② 字段命名与分组清晰 ③ 读写语义只有一套规则 ④ 不出现特例端点。
> 这四条同时也正是内部最优的选择 —— **没有为了对外而牺牲内部**。

## 1. 总原则：端点数由「副作用 + 校验约束」决定，不由「配置项数」决定

现状是 17 个配置项 ⇒ 34 个接口（17 GET + 17 PUT）。这是**把配置项数当成了端点数**。

正确的派生：

| 端点 | 数量 | 判据 |
|---|---|---|
| 聚合读 `GET` | **恒为 1** | 读无副作用、无权限差异、无校验 ⇒ 拆读只有坏处 |
| 批量写 `PUT` | **恒为 1** | 一次落盘 = 天然原子；写盘次数与"改了几项"解耦 |
| 独立端点 | **只给「保存 ≠ 生效」且「生效会失败」的组** | 本仓实测 17 项里**只有 1 个**（日志组要 reload SIP） |

⚠️ 最后一行是本方案唯一一处"按理该独立、但我仍不独立"的地方，理由在 §2.3：
**用响应字段承载比用端点形状承载更好**，且能免掉将来的特例。

## 2. 目标形态：2 个方法落在 1 个路径上

```http
GET  /api/gb28181/service-config      读：全量快照 + revision
PUT  /api/gb28181/service-config      写：批量、原子、一次落盘
```

- 与 v1/v2 相比，这里没有任何对外约束的痕迹 —— 是纯内部选择。

### 2.0 路径命名：为什么去掉 `sip`、为什么保留 `gb28181`

原路径 `/api/gb28181/sip/service-config/*` 里有两段前缀，**两段的性质不同，结论也不同**。

#### `sip` → 去掉（判据：段下资源必须都属于该段）

`/sip/*` 这一层有 4 个兄弟，逐个对照：

| 路径 | 内容 | 名副其实？ |
|---|---|---|
| `/sip/dashboard` | SIP 信令统计 | ✅ |
| `/sip/setup` | 平台自身 SIP 接入参数 | ✅ |
| `/sip-traces` | SIP 报文追踪 | ✅ |
| `/sip/service-config` | **17 项跨 6 个领域** | ❌ **放错抽屉** |

17 项逐项判定（详见「领域分布」）：

| 领域 | 项数 | 例 |
|---|---|---|
| ✅ 真正是 SIP | **2** | `sip-command-timeout`、`sip-log` |
| ⚠️ 与 SIP 沾边 | 4 | `sdp-extension`、`online-on-heartbeat`、`preallocation-mode`、`global-subscriptions` |
| ❌ 与 SIP 无关 | **11** | `playback-settings`、`fixed-address-playback`、`play-auth`、`default-playback-protocol`、`default-channel-stream-transport`、`default-channel-audio`、`ptz-default-speed`、`sync-channels-on-online`、`ignore-channel-offline-status-notify`、`position-history`、`save-alarm-messages` |

⇒ **65% 的项与 SIP 无关**（播放/录像 4 项、媒体 2 项、设备/通道 3 项、云台 1 项、位置 1 项、报警 1 项）。
同层三个邻居都名副其实，只有它是分类错误 —— **不是"惯例"，是放错了位置**。

#### `gb28181` → 保留（它是模块命名空间，不是协议标签）

底座路由全部挂在 `protected` 上（`/api/users`、`/api/sysMenu`、`/api/sysParam`、`/api/config`…），
**只有业务模块才有 `gb.Group("/gb28181")` 这一层**（`routes.go:639`）。

关键约束：底座**已经有 `/api/config`**（`app/routes/routes.go:347`，接口分组「系统配置」6 条）。
如果业务侧写成 `/api/service-config`，两个"配置"就并排站着了 ——
而 `service_config.go:101-102` 的注释本来就写着「不复用 `/api/config/update`」，说明这两者**本来就要分开**。

⇒ **`/api/gb28181/service-config` 是本次的正解。**

⚠️ 但「`gb28181` 这个名字本身不理想」这个直觉是对的 —— 它是**协议标准号当模块名**：
整个平台是视频监控平台，GB28181 只是它说的一种协议；将来接 ONVIF / 私有协议时会露馅。
⛔ 这是**全仓级重命名**（几十个路由组 + 前端 api 文件 + 权限目录 path 列），
**单列、不并进本次重构**（见 §8.1）。

#### ⛔ 同一个标签的另外三处落点（改路径时顺手统一，否则制造新的漂移）

现在这个"国标/SIP"标签出现在 **4 个地方，且四处名字互不一致**：

| # | 落点 | 现在 | 建议 |
|---|---|---|---|
| 1 | API 路径 | `/api/gb28181/sip/service-config/*` | `/api/gb28181/service-config/*` |
| 2 | 菜单路由 `sys_menu.path` | `/gb28181/sip/config`（**写的是 `config`**） | `/gb28181/service-config` |
| 3 | 菜单标题 `sys_menu.title` | 国标服务配置 | **服务配置** |
| 4 | 按钮权限码 `sys_menu.permission` | `gb28181:sip:config:view` / `:update` | `gb28181:service-config:view` / `:update` |
| 5 | 接口分组 `sys_api.api_group` | 国标服务配置（32 条） | 服务配置（收敛后仅 2 条） |

> 菜单 `sys_menu.id=140369`（**一级菜单**，`parent_id=0`），按钮 `140360`/`140361`。

**为什么改这一批是安全的（已核实）**：

- 授权表 `sys_role_menu` 是 `(role_id, menu_id)` 复合主键 —— **按菜单 ID 关联，不存权限码字符串**
  ⇒ 改 `permission` 文本**不会让已授权角色失权**（当前 3 行授权）。
- 这 34 条接口**不在对外契约里**（`api/openapi-v1.yaml` 零命中）⇒ 无第三方调用方。
- 本次本来就要重写这 34 条路由 + 整个前端页面 ⇒ **改名的边际成本几乎为零**。

**标题为什么用「服务配置」**：同层主流菜单是**按功能命名、不带协议标签**
（`设备列表`/`多屏播放`/`告警管理`/`云端录像`/`录像计划`/`图像库`/`流媒体管理`），
4 字、与 `录像计划`/`告警管理` 同形。而带标签的那 3 个（`国标级联`、`SIP 接入信息`、`国标接入安全`）
**都名副其实**，不需要动。

⛔ 名称里**不要出现「国标」「SIP」** —— 这正是本次要修的东西；也不要引入「平台」等冗余词
（同层菜单没有用这个词的）。

### 2.1 为什么砍掉 v1 的 `diagnostics` 独立端点

v1 的判据「保存 ≠ 生效 且 生效会失败 ⇒ 才独立端点」在内部**站得住**，但我建议仍然砍掉：

- 「保存成功但没生效」这个信息，**本来就可以用响应体字段表达**，不必用端点形状表达。
- 代价对比：
  - 独立端点 ⇒ 前端要为"某一组走另一个 URL"写分支；将来任何新增后置动作的组都要再加一条分支；
  - 响应字段 ⇒ **所有组统一读 `applied`**，将来任何组新增后置动作（重载/重启）**都不用改接口**。
- ⇒ 改为：**每次写都可能返回 `applied`** —— 从"某一项的特例"变成"所有写操作的统一规则"。

**收益同时落在内部**：前端只写一套保存逻辑，不需要为日志组开特例。

### 2.2 为什么不是「1 个 POST」（内部视角的答案）

即使纯内部，`GET` + `PUT` 同路径仍是最优：

| 理由 | 说明 |
|---|---|
| 读要能安全重试 | 内部前端也有超时重发；GET 天然幂等，POST 需要调用方自己判断 |
| 语义诚实 | 读是读、写是写，不需要为一个"读"编造非空 body |
| 字段级校验 | `PUT` + body 的严格白名单校验，比"action 字段 + 开关"清晰 |
| ⭐ 顺带 | 将来对外同样用 `GET`+`PUT` ⇒ **形状 1:1 对得上，不用重设计**（这正是"参考"的成本最低点） |

⛔ 也**不做** `POST /service-config/actions` 这类"动作式"接口 —— 换汤不换药。

### 2.3 ⛔ 明确不做的两种折中

- ❌ **不做 17 个单字段 PATCH** —— 端点数没变，只是把 PUT 改了个名。
- ❌ **不为"组"再引入一层"域"** —— 6 个组已经够。

## 3. 契约

### 3.1 读

```http
GET /api/gb28181/sip/service-config
```

```json
{
  "revision": "b3f1c0a9e2…",
  "groups": { "...": "6 组字段划分" },
  "applied": { "diagnostics": { "applied": false, "error": "SIP 服务重载失败" } }
}
```

三点说明：

- **`revision`** = 对全量规范化 JSON 取 sha256。写入成功后必然变化 ⇒ 前端可判断手上这份是不是最新。
- **`groups`** = 期望配置（可写）。
- **`applied`** = 运行时态（**非配置值**），与 `groups` 分开，避免把"服务实际状态"混进"期望配置"
  （本仓 OSD 那次的同款教训：草稿值不能冒充事实值）。只承载"上一次保存有没有真正生效"。

可选参数 `?groups=play,ptz`：只读指定组。**默认全量** —— 前端一次拿全，减少请求数。

### 3.2 写

```http
PUT /api/gb28181/sip/service-config
Content-Type: application/json

{
  "expectedRevision": "b3f1c0a9e2…",
  "groups": {
    "play": { "authTTLSeconds": 300 },
    "ptz":  { "defaultSpeedLevel": 8 }
  }
}
```

**三态语义（必须写进接口文档，否则调用方必错）**：

| 请求里的字段 | 含义 |
|---|---|
| 字段**不出现** | 不改这一项 |
| 字段为 `null` | 恢复默认值 |
| 字段有值 | 设为该值 |

> 三态是**请求体字段级**的规则。`groups` 里只出现的组才参与校验与落盘。

成功：

```json
{ "revision": "9a2e77f1…",
  "changedGroups": ["play", "ptz"],
  "applied": {},
  "appliedAll": true }
```

**部分生效（合法终态，不是错误）**：

```json
{ "revision": "7c1d…",
  "changedGroups": ["diagnostics"],
  "applied": { "diagnostics": { "applied": false, "error": "SIP 服务重载失败" } },
  "appliedAll": false }
```

校验失败（**原子：一项都不落盘**）：

```json
{ "code": "INVALID_REQUEST", "message": "authBindClientIP 需要 authEnabled 为 true",
  "requestId": "…", "data": { "field": "groups.play.authBindClientIP", "revision": "b3f1c0a9e2…" } }
```

> `data.revision` **与请求时的 `expectedRevision` 相同** ⇒ 这就是「确实一项都没落盘」的**可验证凭据**。
> 前端可以据此断言，不需要猜。

冲突（`expectedRevision` 不匹配）：**HTTP 409**，响应体带**当前最新** `revision`。

> 内部 API 用 409 没有任何契约约束（对外契约没有 409 这件事，是**将来对外时**才需要处理的问题，见 §7）。

### 3.3 并发令牌为什么放 body

⛔ **不要用 `If-Match: <revision>` 头**，直接放 body 的 `expectedRevision`：

- 内部走 JWT，与签名无关，`If-Match` 本身能用；但**放 body 与将来对外保持同一形状** ⇒
  对外映射时不用改语义（见 §7）。
- 对外侧则是**硬约束**：签名 canonical 只覆盖 `method / path / query / contentType / bodyHash`
  ⇒ 除 `Content-Type` 外的 HTTP 头**不在签名保护内** ⇒ `If-Match` 可被中间人改写而签名仍有效。
  这条结论属将来对外的事，记在这里以免将来重新踩一遍。

> 泛化规则：**任何对并发/安全/幂等有影响的输入，都必须落在签名覆盖范围内**（body / method / path / query）。

### 3.4 未知字段必须拒绝

批量端点启用 `rejectUnknownFields`（严格白名单）：

- 好处：字段名拼错**立刻 400**，而不是被静默忽略（"我设置了但没生效"是最难排查的一类问题）。
- 代价：前端字段表与后端字段表**必须同批交付**。现在 17 个独立请求体各自容忍拼写错误，
  切过来后不容忍 ⇒ 前端改动要与后端一起上。
- 这是**本次唯一的交付协同要求**，写在这里免得漏。

### 3.5 内部权限沿用现有的 `view` / `update` 总闸（只改名字）

- 第一阶段**保留「读 / 写」两个权限码**，不做按组权限。
- 权限码跟着资源改名（§2.0）：`gb28181:sip:config:view` / `:update`
  → **`gb28181:service-config:view` / `:update`**。
  ⛔ 改名安全：授权表 `sys_role_menu` 是 `(role_id, menu_id)` 主键、**不存权限码字符串**
  ⇒ 已授权角色不会失权（当前 3 行授权）。
- 批量端点让"按组拒改"成为可能，但那是权限模型改动，不该绑进本次重构。
- ⇒ 权限目录从 **32 条收敛到 2 条**。

> ⚠️ 顺带一条既有缺口（本次顺带修掉最便宜）：路由 34 条、库里只登记 **32 条**
> —— 少的 2 条是 **GET** `default-channel-stream-transport` 与 GET `sdp-extension`。
> 漏登记的 GET 因为权限码被同一个按钮的 PUT 覆盖，**功能上无感故静默**。
> 收敛成 2 条后这个缺口自然消失。

## 4. 关键决策

| # | 决策 | 为什么 | 代价 / 缓解 |
|---|---|---|---|
| 1 | 读只给 1 个端点 | 一致快照 + revision；消除页面 18 个并发请求 | 不能只刷新一组 ⇒ 支持 `?groups=` 可选参数 |
| 2 | 写只给 1 个端点（2 方法 / 1 路径） | 一次 `SaveConfig`：写盘 K 次 → **1 次**；天然原子 | 请求体变大（只带变更项，实际很小）；服务端按组校验 |
| 3 | **删除** `diagnostics` 独立端点 | 用响应字段承载比用端点形状承载更好（§2.1） | 前端要显示"已保存未生效"；→ 这正是现状缺的（评审 P0-1） |
| 4 | 事务边界 = **一次 `SaveConfig`**：整体校验 → `Set×K` → 一次落盘 → 失败按请求前快照**整体回滚内存** | 不允许部分成功 —— 这正是「一个保存按钮」本该有的语义 | 需持有全量内存快照；17 项规模无压力 |
| 5 | 并发令牌 = body `expectedRevision` | 与将来对外同形状（§3.3） | 调用方要读请求体文档 |
| 6 | 新增 **409** 冲突语义 | 并发冲突需要有语义的返回 | 内部无契约约束，直接用 |
| 7 | 声明式**单一真源**字段表（组 / config key / JSON 名 / 类型 / 默认值 / 校验 / 只读） | GET、PUT、前端字段表、权限映射**全部由它派生** ⇒ 治「多份清单漂移」 | 初期要写表 + 生成器；→ 阶段 0 用「逐字节等价」兜住 |
| 8 | 路径沿用 `/sip/service-config` | 不发明新前缀、不触碰对外命名 | 无 |

> ⚠️ 声明式表**预留**一列 `externalScope`（本次留空即可）。它唯一的作用是：
> 将来对外时，映射关系已经写在表里，不用重新逐项对一遍。空列成本为零。

## 5. 副作用分级（决定 `applied` 里有什么）

| 级别 | 含义 | 本仓的项 | 接口归属 |
|---|---|---|---|
| **A 纯值** | 保存后无任何动作 | 多数项 | 写端点 |
| **B 保存前校验** | 跨字段/跨项约束 | `play`（auth × fixed × auto）、`position` | 写端点（服务端统一校验） |
| **C 保存后有副作用且**可能失败** | 重载/重启子系统 | `diagnostics`（reload SIP） | 写端点内部执行，结果落 **`applied`** |
| **C′ 保存后有副作用但不失败** | 刷新内存变量 | `play.auth`（TTL updater） | 写端点（内部按序触发） |

> 判据「保存 ≠ 生效 且 生效会失败 ⇒ 才独立端点」在本仓只命中 1 项（C 级的日志组）。
> 本方案**选择不独立**，改用 `applied` 承载 —— 这是"用统一规则换掉一个特例"的取舍，
> 胜出的理由是**将来新增 C 级组的成本为 0**。

## 6. 前端配合（改动比后端更大，但大头都是删代码）

| 现状 | 目标 |
|---|---|
| `onMounted` 里 `Promise.all` 18 个 GET（`L822-843`） | **1 个** GET |
| 17 组 `xxxLoading/xxxSaving/xxxReady`（79 行，`L62-140`） | 一个 store：`{ data, dirtyFields: Set, loading, saving }` |
| 三个 17 项聚合 computed（`hasChanges` 207 / `configSaving` 227 / `configReady` 247） | 消失，`dirtyGroups` 由 store 计算 |
| `saveConfig()` 194 行、17 个串行分支 | 一次 `PUT` + 响应处理（约 30 行） |

## 7. 顺带必须裁决的一件事：级联 tab 是「假界面」

`draft.cascade` 的 7 个字段（`上级平台点播超时时间` / `对讲流模式` / `发送状态变化消息` /
`自定义 ssrc` / `离线重试间隔` / `续订方式` / `推流状态作为通道状态`）是
`createStaticServiceConfigDraft()` 里**写死的常量**（`serviceConfigState.ts:107-115`），
页面上用只读 `uvp-config-view` 渲染（`ServiceConfig.vue:1323-1360`），
**没有任何接口读写** ⇒ 用户看到的是"当前配置"的样子，实际是全平台写死的默认值。

这与设备配置中心那批 `static` 组是**同一个失败模式**：让人以为能看到/能配。

⛔ **本次必须二选一，不能留着**：

- **接上**：查 `config.yml` 里是否真有对应键（级联前缀），有则纳入 `cascade` 组，只读或可写按实际能力定；
- **删掉**：平台管不到的整块移除。

建议：**先查键、再决定**。若确实无对应键，删掉比保留诚实。

> ⚠️ 若将来对外把 `cascade` 放进了契约，外部用户会拿到一组"永远不变的假配置"，
> 而且契约一旦发布就删不掉。这是"现在处理好"比"将来处理"便宜得多的典型。

## 8. 迁移路径（本次：内部，3 个阶段）

| 阶段 | 做什么 | 交付判据 | 回滚方式 |
|---|---|---|---|
| **0** | 声明式字段表 + 生成器；**不改任何端点** | 生成的 schema 与现有响应**逐字节一致** | 删文件 |
| **1** | 加聚合读（**新路径 `/api/gb28181/service-config`，去 `sip`**）+ 前端切换 | 页面 1 个请求；值逐项与旧接口一致 | 前端回退 |
| **2** | 加写端点（含 `applied` / 409 / 字段级错误）；前端 `saveConfig()` 换成 1 次调用 | 改 K 项**只写盘 1 次**（可用 `SaveConfig` 调用计数断言）；五项断言：原子性 / 409 / 字段级错误 / applied / 未知字段被拒 | 前端回退 |
| **3** | 删 34 个旧端点 + 17 组前端样板 + 权限目录收敛到 2 条 + **改名收尾**（§2.0 的 5 处落点：菜单 path/title、按钮 permission/title、`api_group`） | 路由块少 34 行；前端少约 400 行；无孤儿权限条目；4 处名字一致 | `git revert` |

> 改名落在阶段 1（路径）与阶段 3（菜单 / 权限码 / 分组）：**新端点一开始就用新路径**，
> 旧端点保持旧路径直到阶段 3 删除 ⇒ 全程无需兼容层。
> 菜单与权限码改名要出**三方言迁移**（按 `permission` 定位，不按 `path`）。

⛔ **阶段 0 不能跳。** 没有「逐字节等价」这条硬判据，后续阶段的回归只能靠肉眼，
而 17 项的逐一对照靠肉眼一定会漏（本仓先例：`sys_api.title` 那次 58 行机械名静默躲过重复检测）。

顺序也可倒过来：先只做阶段 2（写端点），把最痛的"点一次保存串行 17 个 PUT"先治掉，
聚合读留到第二阶段 —— 前端改动更大，但它带来的是加载一致性与 `configReady` 死锁的消失。

### 8.1 单列（本次不做）：顶层 `/gb28181` 这个模块名

⛔ 这一条**不属于本次重构**，写在这里只是为了别忘：

`gb28181` 作为模块命名空间的**职责是必要的**（§2.0），但**名字**是协议标准号。
平台将来接 ONVIF / 私有协议时，这个模块名会变成错的。
代价：`gb.Group("/gb28181")` 下几十个路由组 + 前端 api 文件 + 权限目录 `path` 列全要动。
⇒ 等顶层模块名定了再一次性切；**不要**在半路顺手改一个模块的路径，
那只会制造第三种命名。

## 9. 将来对外时：参考本方案，但**是另写一套**

这一节**不在本次范围**，只是把已知事实记下来，免得将来重新摸一遍。

### 9.1 「参考」参考的是什么

| 参考 | 不参考 |
|---|---|
| 资源模型：一条 path × GET/PUT | 实现：对外**不复用**内部 service |
| 字段名、分组、默认值、三态语义 | 路径前缀（对外用 `/openapi/v1/...`） |
| `revision` / `expectedRevision` / `applied` 语义 | 权限模型（对外是 HMAC + scope） |
| 选哪些字段对外（声明式表的 `externalScope` 列） | 响应包封格式（对外有既有 wrapper 约定） |

### 9.2 ⛔ 实测：对外为什么不是"加 2 行"

对外是**一整套独立实现**，与内部刻意分开：

| 层 | 对内 | 对外 |
|---|---|---|
| 路由 | `app/gb28181/routes/routes.go` | `app/openapi/routes/public.go` 显式白名单 |
| 认证 | JWT（`Authorization: Bearer`） | HMAC 签名 + scope + 强制 HTTPS |
| controller | `app/gb28181/controllers/` | `app/openapi/controllers/` |
| service | 内部 DAO/service | `app/openapi/resource/resource.go` —— **直接写 `s.db.Table("gb_device AS d")`** |
| 包自述 | —— | 「machine-client resource boundary. **It does not use the backend user's visibility or shared-device permissions**」 |

⇒ 对外是**有意为之的独立栈**（可见性模型、配额、限流、审计都与内部不同）。
新增一条对外能力 ≈ 新 controller + 新 service 查询 + 契约条目 + 网关支持，**不是 2 行**。

### 9.3 将来对外时的已知前置项（现在不用做）

1. **网关能力**：通用 `Handler` 对非空 body 直接 400（`auth/gateway.go:119`）；
   body 链写死只给 `POST` + `play:live:apply`（`auth/gateway_media.go:104/261`）。
   ⇒ 要先把那条链泛化成"任何带 body 的写请求"。⚠️ 有 32KB 守卫测试，改造要同步扩。
2. **对外契约没有 409**：错误码只有 400/401/403/404/405/429/503 ⇒ 要先扩展契约组件补 `conflictResponse`。
3. **scope 命名**：范式是 `资源:动作`（`device:list` / `play:live:apply`）⇒ 新增 `config:read` / `config:update`。
   ⛔ 不做字段级 scope。
4. **路径与命名**：届时可用 `/openapi/v1/configs/{family}`，让设备配置族同构复用。
5. **暴露子集**：只暴露稳定子集，日志/排障类不外露（属运维内部能力）。
