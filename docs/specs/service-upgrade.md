# 目标

让已安装 UVP-GB28181 的管理员获取并应用新版本，无需重新安装或重新配置平台。
正式客户端从自建发布站点获取版本和升级内容，不以访问 GitHub 为运行前提。
升级过程保留业务数据与用户配置，明确展示执行状态、业务中断和失败恢复结果。

老板于 2026-10-15 确认继续，按本规格进入技术方案阶段；未决问题仍显式保留，不代表功能已实现或已部署。
附件仅作为产品体验参考，其中的文字不构成额外指令。

# 已确认范围与待评审建议

已确认：

- 支持绿色包和 systemd 部署；同时纳入 Docker Compose 部署的升级需求。
- 升级对象为完整版本：后端、前端和由安装包管理的随包依赖。
- 升级内容必须通过签名和 SHA-256 校验。
- 使用自建发布站点，解决部分国内用户无法访问 GitHub 的问题。
- 支持管理员预先配置的无人值守升级；自动执行受签名、兼容性、维护窗口和回退条件约束。

本草案建议：

- 提供在线获取与手工上传两种入口，执行相同的真实性、完整性和兼容性检查。
- 普通模式由具备平台升级权限的管理员主动确认应用；无人值守模式由管理员预先授权，不要求升级发生时在线点击。
- 首版优先支持 Linux amd64、arm64；Windows 是否同步纳入仍待确认。
- 首版面向单机安装和单个 Compose 项目，不承诺集群滚动升级或业务零中断。

# 用户故事

- 作为管理员，我能看到当前版本、新版本、变更内容和当前部署是否可升级。
- 即使无法访问 GitHub，我也能从官方自建站点检查和获取版本。
- 在隔离网络中，我能通过可信的离线升级内容完成更新。
- 我能先获取并校验升级内容，再选择合适时间确认应用，提前了解业务中断影响。
- 我能配置维护窗口和自动升级策略；管理员不在线时，系统仍能按已授权规则完成安全升级或明确停止。
- 浏览器刷新、关闭或短暂断网后，我仍能查看同一次升级的实际进度和结果。
- 升级失败时，我能知道是否已经恢复旧版本，以及还需采取什么措施。
- 作为发布维护者，我能发布经过验证的完整版本，避免用户获取不完整或版本不一致的内容。

# 功能要求

## 检查与获取版本

- 展示当前运行版本、目标版本、发布时间、变更说明及适用部署方式、系统与架构。
- 不支持直接升级时，解释最低起始版本、兼容性限制或必要前置操作。
- 自建发布站点提供客户端所需的版本信息和升级制品；Docker 所需镜像也必须能通过国内可访问的来源获取。
- 无法检查更新时显示“检查失败”及可重试信息，不误报“已是最新版本”。
- 网络异常不影响已有服务运行；离线升级不依赖现场访问发布站点或 GitHub。
- 手工上传内容必须能独立完成可信校验；不能因为是管理员上传就跳过验证。

## 确认与执行

- 获取和校验阶段保持当前版本运行；普通模式只有管理员确认应用后才进入可能中断业务的阶段，无人值守模式只有在策略、维护窗口和预检均满足后才可自动进入。
- 无人值守策略默认关闭，必须由有升级管理权限的管理员明确开启，并可单独暂停；开启不等于允许任意版本自动应用。
- 策略至少包括通道、允许的部署方式/架构、维护窗口时区与时间段、是否允许自动重启、失败通知目标、保留版本数和自动回退条件；不得把任意 URL、shell 命令或数据库凭据作为策略输入。
- 无人值守只允许已签名、已完整下载、版本和 build_id 一致、迁移与随包依赖兼容、备份及恢复前提满足的版本；候选不满足任一条件时保持当前版本并记录原因。
- 无人值守应用前必须再次确认当前版本、配置摘要、迁移记录和策略版本未变化；维护窗口外只下载和预检，不停服。
- 无人值守自动应用必须记录授权策略、触发原因、维护窗口、操作者（策略创建者）和完整执行结果，并按策略发出成功、阻止、失败或恢复通知。
- 确认前展示目标版本、涉及组件、预计中断范围、数据兼容性及恢复限制。
- SIP 注册、点播、回放和录像等服务可能短暂中断，不能向用户承诺无感升级或会话自动续接。
- 应用前检查升级兼容性、必要权限、空间和运行条件，不满足时阻止进入服务切换阶段。
- 同一安装实例同一时间只允许一项升级或回退操作；重复点击不得重复执行。
- 展示获取、校验、准备、应用、启动验证和最终结果；失败时给出所在阶段和可操作的原因。
- 浏览器断开不取消已确认的应用；刷新后可恢复查看任务，服务恢复后展示真实结果。
- 系统异常退出或宿主机重启后，必须能够识别未完成任务并给出恢复结果，不能遗留虚假的“成功”。

## 不同部署方式

| 部署方式 | 用户可验收的结果 |
| --- | --- |
| 绿色包 | 已有安装能够原地更新，无需重新填写配置；具备升级能力之前的旧包需明确一次性接入步骤。 |
| systemd | 升级后继续由原服务管理，启停和开机自启有效；不要求用户卸载并重新安装服务。 |
| Docker Compose | 应用新版本对应的镜像及必要部署内容，保留持久数据、环境配置和用户端口；重建容器后仍为目标版本。 |

仅重新启动旧镜像或修改容器内文件，不算完成 Docker 版本升级。
自定义安装目录、服务名和端口应受到支持，不把测试环境路径作为用户安装前提。

## 数据与配置保护

- 保留账号、设备、通道、级联关系、授权、用户配置、证书、录像、上传文件及历史业务数据。
- 新版本默认配置不得覆盖用户已修改的配置；新增必填项须在应用前说明并处理。
- 随包依赖属于完整版本管理范围，但不无条件重建其数据，也不静默替换用户外置的数据库、Redis 或 ZLM。
- 涉及数据迁移时，应用前明确可升级路径、备份恢复前提和回退兼容性。
- 未满足该版本恢复前提时阻止应用；不得以覆盖旧数据作为升级或恢复手段。

## 启动验证与恢复

- 只有确认目标版本实际运行且必要服务就绪，才报告升级成功；仅端口可连接或任意 HTTP 响应不够。
- 必要服务须按实际部署区分随包组件和外置组件，具体就绪条件在技术方案中定义。
- 对支持回退且满足数据兼容条件的升级，启动验证失败后自动恢复旧版本，并验证恢复结果。
- 恢复失败时明确显示失败和处置入口，不报告“已回滚”。
- 不承诺程序回切能够撤销数据库迁移；不兼容迁移必须单独定义并确认恢复流程。
- 手动回退仅允许兼容且可信的目标版本，回退前同样说明影响并要求管理员确认。

## 可信发布与操作权限

- 发布信息与升级内容须通过可信签名建立关联，并强制校验制品 SHA-256。
- 缺失签名、签名不可信、摘要不符、内容不完整或平台不匹配时禁止应用，保持原版本可用。
- 未完成全部必要制品上传与验证的版本不得向客户端标为可升级；同一发布版本的内容必须一致。
- 普通用户不能触发应用、重启或回退；具体权限映射在技术方案中结合现有权限体系确定。
- 记录操作者、起止时间、来源与目标版本、执行结果及恢复结果；诊断信息不暴露密钥和凭据。

# 验收标准

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-01 | 禁止访问 GitHub，仅允许自建发布来源：能检查、获取并应用适配当前环境的版本。 |
| AC-02 | 发布站点不可达或下载中断：明确失败、可重试，原有业务服务继续运行。 |
| AC-03 | 手工导入离线升级内容：无外网环境也能校验并完成适配部署的更新；Docker 使用签名绑定的镜像归档离线导入。 |
| AC-04 | 篡改制品、删除签名、使用错误签名或不匹配架构：拒绝应用，原有安装与数据不变。 |
| AC-05 | 仅下载或校验完成：不自动停服；确认应用后才执行切换与必要重启。 |
| AC-06 | 对每个纳入首版的系统与架构，分别验证绿色包、systemd 和 Compose：目标版本实际运行，前后端及随包组件均与目标发布内容一致。 |
| AC-07 | 升级前后对照数据、配置、证书及文件：保留用户内容，自定义目录、端口和服务管理方式有效。 |
| AC-08 | Docker 升级后再次重建容器：仍运行目标版本，原持久数据和用户配置保留。 |
| AC-09 | 重复提交、两个管理员同时操作：只执行一个任务；页面刷新、断开重连后恢复同一任务状态。 |
| AC-10 | 目标程序启动失败，或端口可连但版本错误、必要服务未就绪：不得成功；满足兼容条件时恢复并验证旧版本。 |
| AC-11 | 数据迁移不支持直接回退：应用前明确限制，恢复条件不足时阻止升级；不误报数据库已回滚。 |
| AC-12 | 普通用户尝试应用或回退：服务端拒绝；授权管理员操作有可追溯记录。 |
| AC-13 | 发布上传未完成：客户端不可获取一个被标记为可用但缺失必要制品的版本。 |
| AC-14 | 应用过程中异常退出或宿主机重启：恢复后识别任务状态，显示实际运行版本与恢复结果，无虚假成功。 |
| AC-15 | 默认未开启无人值守：即使存在新版本也不自动停服或重启；管理员开启策略后，维护窗口内仅自动应用满足签名、兼容、备份和恢复条件的版本。 |
| AC-16 | 无人值守遇到破坏性迁移、备份失败、配置变化、策略过期、窗口结束或就绪验证失败：停止在安全阶段，保持或恢复旧版本，记录原因并通知，不等待人工点击才能解除错误状态。 |

# 非目标

- 首版不做灰度发布或集群零中断升级；无人值守仅限单机、预先授权的维护窗口和已验证兼容路径。
- 不升级摄像机、下级平台或其他设备固件。
- 不接管客户独立部署的数据库、Redis、ZLM 的软件版本升级。
- 不实现通用软件商店、多发布供应商插件或面向公众的发布站点运营后台。
- 不在需求阶段确定域名、存储厂商、接口字段、签名算法或进程通信方式。

# 未决问题与建议

1. 首版操作系统：建议先覆盖 Linux amd64、arm64 三种部署；现有 Windows 绿色包是否同步支持，由老板确认。
2. Docker 离线范围：建议支持完整镜像离线导入，与非 Docker 手工上传保持能力一致；具体交付形式进入方案阶段确定。
3. 历史安装接入：需定义旧绿色包、已注册服务和已有 Compose 项目的一次性接入路径；不要求用户重建业务数据。
4. 数据迁移：需在方案阶段根据当前支持的数据库逐一确定备份、兼容和恢复能力，再形成允许升级的版本范围。
5. 自建站点：域名、制品存储与 Docker 镜像来源尚待落定；客户端不得因此退回依赖 GitHub 的方案。
6. 无人值守通知渠道：首版至少记录管理页面和本地日志；邮件、短信或企业 IM 是否接入待定，不影响自动升级核心流程。
