# 服务升级进度可视化

依据：老板已确认 docs/specs/service-upgrade-progress.md 范围。
状态：老板已确认方案与任务清单；实现及本地验收完成，结果见任务清单。

## 实现范围

以前端改动为主，复用现有导入状态查询和升级任务查询，不新增服务端协议或升级执行阶段。

- 上传接口增加可选进度回调，透传 Axios 的实际上传事件；调用方继续使用现有上传请求与超时设置。
- 服务升级页保存本次文件名、大小、已传字节和传输状态。上传到 100% 后显示“文件已传输，等待服务端受理”，收到任务标识后切换后台状态查询。
- 新增一个页面专用的进度展示组件，复用 Arco 进度条及现有主题变量；显示导入进度和升级任务进度，任务详情复用同一展示组件。

## 页面布局

将现有离线导入提示和活动任务提示整理为紧凑的进度区域，放在顶部版本卡之后。空闲且没有任务时不增加占位内容。

- 导入：上传升级包 → 后台校验 → 升级包就绪。上传期间显示百分比、已传/总大小和文件名；无可靠总大小时只显示已传大小与处理中状态。
- 应用：准备与授权 → 备份数据 → 执行迁移 → 切换与验证 → 完成。分组避免横向堆叠过多节点，当前节点下仍显示服务端的具体阶段，如“停止服务”“验证启动”“提交升级结果”。
- 等待应用授权使用明确的等待提示，保留原有确认应用入口。最终状态展示成功、失败、已回退或需要恢复；失败原因按现有详情入口展开。
- 桌面横向排列，窄屏纵向排列；文字和图标同时表达状态，适配明暗主题。

## 数据与恢复

- 上传百分比仅用于文件传输，不换算成整体升级百分比。不估算后台阶段百分比及剩余时间。
- 导入复用现有任务标识与后台轮询；恢复已受理任务时不虚构上传速度或本次已传字节。
- 升级任务以 task_id 关联；顶部优先显示活动任务，终态仍可从最近任务或记录详情查看，不能将其他任务的成功结果套到当前任务。
- 请求失联时保留最后已知阶段并标明“正在重连”，成功状态必须来自最新可信结果；恢复后更新同一任务。沿用现有应用授权、权限及前端版本刷新机制。
- 未知阶段按原值提示，不映射为已完成；已回退不显示目标版本升级成功。

## 验证与交付边界

先补 API 回调透传和页面行为测试，确认失败后实现；覆盖上传中、上传完未受理、校验中/失败、刷新恢复、执行阶段、断线重连、成功与回退。再运行升级相关回归和前端生产构建，并在可登录的开发页面检查真实渲染、窄屏和明暗主题。

本次不修改已交付的 1.1.5 制品，不重启或替换 220 正在验收的服务；部署和出后续版本另按老板指示执行。
