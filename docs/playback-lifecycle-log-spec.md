# 播放生命周期日志需求规格

- 状态：已确认
- 日期：2026-09-21
- 当前范围：GB28181 实时点播

## 1. 背景

现有调度日志只能证明调度器是否选出媒体节点，不能证明 SIP INVITE、RTP 收流、媒体流就绪或客户端实际播放成功。

现有点播尝试统计能区分“进行中、媒体就绪、失败”，业务日志也覆盖若干关键阶段，但缺少一条可查询、可关联、可审计的完整播放时间线。因此播放失败时，运维人员仍无法在一个页面内回答“失败发生在哪一阶段、具体原因是什么、后续清理是否完成”。

GB/T 28181-2022 明确区分 SIP 会话通道与 RTP/RTCP 媒体通道；收到 SIP 成功响应不等于已经收到媒体。本功能必须保持这一事实边界。

## 2. 目标

1. 为每一次实时点播建立稳定且唯一的生命周期标识，并贯穿请求、调度、SIP、媒体、客户端反馈和停止清理阶段。
2. 以阶段事件记录可观测事实，不再用单一“成功/失败”概括整个播放链路。
3. 任何终止性失败都能定位到明确阶段，并提供稳定原因码和经过脱敏的原因说明。
4. 运维人员能够按时间、设备、通道、流、节点、生命周期状态、失败阶段和关联标识查询日志。
5. 在详情中按时间顺序还原一次点播从发起到结束的全过程，并明确区分已证实、失败、进行中和未知。

## 3. 用户故事

1. 作为运维人员，我能看到一次点播是否完成节点选择、RTP 资源分配、INVITE 应答、媒体流就绪、客户端首帧和停止清理。
2. 作为运维人员，我能从一次失败记录直接看到失败阶段、原因码、原因说明和此前已经完成的阶段。
3. 作为运维人员，我能用设备、通道、流或关联标识找到同一次播放的全部事件，而不需要跨多类文本日志手工拼接。
4. 作为开发人员，我能区分 SIP `200 OK`、ZLM 流注册、媒体可用和浏览器首帧，避免错误宣称播放成功。
5. 作为审计人员，我只能看到自己数据权限范围内的设备播放记录，且日志不泄露密钥、令牌、完整播放地址或敏感网络参数。

## 4. 生命周期事实模型

### 4.1 阶段

一次实时点播至少覆盖以下事实阶段：

1. 请求已接收。
2. 设备与通道校验完成，或校验失败。
3. 已复用现有媒体流，或已完成媒体节点选择。
4. RTP 接收资源已分配，或分配失败。
5. INVITE 已发出。
6. 设备已接受、拒绝或未在期限内响应 INVITE。
7. 媒体流已在目标节点注册并确认可用，或等待媒体超时。
8. 播放地址已签发，或播放授权失败。
9. 客户端已报告首帧，或客户端报告播放错误；未上报时保持未知。
10. 停止已请求。
11. SIP 会话、RTP 资源和持久化状态清理完成，或清理部分失败。
12. 生命周期结束。

### 4.2 状态语义

- `已证实`：有对应服务端或客户端证据。
- `失败`：该阶段产生明确错误、拒绝或超时证据。
- `进行中`：生命周期尚未到达终态，且仍在允许期限内。
- `未知`：没有足够证据，不能推断成功或失败。
- `不适用`：例如复用已有流时，不要求再次分配 RTP 或发送 INVITE。

页面不得使用一个没有限定语的“播放成功”表示所有阶段。必须分别展示“媒体已就绪”和“客户端首帧已确认”。

## 5. 记录要求

每个阶段事件必须具备：

- 生命周期标识、事件时间、阶段、事实状态和事件名称。
- 设备编码、通道编码；已知时包含流标识和媒体节点标识。
- 是否复用现有流。
- 稳定原因码；失败时包含经过脱敏和长度限制的原因说明。
- 已知时包含 SIP Call-ID、CSeq 和内部关联标识。
- 从生命周期开始到当前事件的耗时；终态包含总耗时。
- 事件来源，用于区分 HTTP、播放服务、SIP、ZLM Hook、客户端反馈和清理任务。

重复回调、重试和并发请求不得制造互相矛盾的终态。相同事实允许幂等接收，但查询结果必须能识别重复或只呈现一次有效状态。

## 6. 查询与展示

1. 提供独立的“播放日志”视图，不与“调度日志”混用。
2. 列表默认按最近事件时间倒序，默认每页 10 条，滚动条位于表格内部。
3. 列表至少展示开始时间、设备/通道、流、节点、媒体状态、客户端状态、当前/最终阶段、耗时和失败摘要。
4. 支持按时间范围、设备、通道、流、节点、生命周期状态、失败阶段和关联标识筛选。
5. 点击一条记录后展示阶段时间线；未发生、未知、不适用和失败必须有不同语义，不得都显示为空白或失败。
6. 复用流必须显式标识，并展示“复用确认媒体可用”的证据，不能伪造一次新的 INVITE 生命周期。
7. 页面查询失败时不得把上次数据或无数据呈现为 0 次失败；应明确显示数据不可用或保留上次样本。

## 7. 权限与安全

1. 查询结果继承设备数据权限，不能通过关联标识、流标识或节点筛选绕过权限。
2. 播放令牌、API Secret、Authorization、完整内部 URL 和凭据不得写入或返回日志。
3. 错误说明必须使用安全展示规则；稳定原因码用于统计，原始底层错误不得直接暴露给无权用户。
4. 客户端反馈只能更新与当前用户、当前播放授权和当前生命周期匹配的记录，过期或伪造反馈不得改变状态。

## 8. 可靠性与保留

1. 生命周期日志写入失败不得阻塞或改变真实播放控制结果，但必须产生可监控的持久化失败信号。
2. 进程退出、请求取消或客户端断开后，已经采集到的服务端事实不得丢失或被改写为成功。
3. 长时间停留在进行中的记录必须被识别为异常未收口，并保持真实原始阶段，不能自动伪造成业务失败。
4. 日志保留和清理必须有明确期限，清理过程不得删除仍在进行中的生命周期。

## 9. 验收标准

1. 新点播成功且客户端正常播放时，能在同一生命周期中看到请求、校验、节点/RTP、INVITE 接受、媒体就绪、播放地址签发和客户端首帧证据。
2. 设备离线、无可用节点、RTP 分配失败、INVITE 拒绝、INVITE 超时、媒体等待超时和播放授权失败分别落在正确阶段，并有不同稳定原因码。
3. SIP `200 OK` 后没有媒体时，最终显示“INVITE 已接受、媒体未就绪”，不得显示为完整播放成功。
4. 媒体已就绪但客户端未反馈首帧时，显示“媒体已就绪、客户端状态未知”，不得显示客户端失败。
5. 客户端明确报告解码或网络错误时，保留服务端媒体就绪事实，同时单独记录客户端失败。
6. 复用已有流时，不产生伪造的 RTP 分配和 INVITE 接受事件；时间线明确标识复用路径。
7. 正常停播时显示清理完成；BYE、关闭 RTP 或状态清理任一失败时，显示清理部分失败及对应原因。
8. 同一生命周期的所有事件使用同一标识，且可关联已知的 stream、node、Call-ID 和 CSeq。
9. 无设备数据权限的用户无法查询、查看详情或提交该生命周期的客户端反馈。
10. 聚焦自动化测试覆盖所有阶段转换、终态幂等、权限隔离、敏感信息脱敏、异常进行中识别和多数据库迁移契约。
11. 通过真实点播链路验收：至少各验证一次成功首帧、INVITE 失败、媒体超时、客户端失败和正常停播；每个结论分别保留 HTTP、SIP、ZLM、客户端或数据库证据。

## 10. 非目标

- 不以调度命中作为播放成功。
- 不以 SIP `200 OK` 作为媒体成功。
- 不从服务端推测浏览器是否解码出首帧。
- 不记录视频内容、音频内容或完整 SDP/SIP 报文；原始协议报文仍由 SIP 追踪能力负责。
- 本规格默认不覆盖历史录像回放、下载、上级级联拉流和第三方播放器；这些链路若纳入，应复用相同事实语义但分别验收。
- 不在本功能中修改点播、调度、SIP 或媒体控制行为。

## 11. 已确认决策

1. **业务范围**：首期覆盖当前讨论对应的“实时点播”，历史回放、下载和级联后续按同一模型扩展。
2. **客户端证据**：纳入受授权保护的首帧/播放错误反馈，分别呈现服务端媒体事实和客户端播放事实。
3. **保留期限**：生命周期汇总保留 30 天，阶段事件保留 7 天。
