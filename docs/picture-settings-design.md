# 画面设置 模块设计

## 0. 本文件的位置

上游 spec 的验收标准 #7 写：

> OSD/遮挡位置和录像周计划有符合任务的操作方式；保留精确数值和秒级时间输入能力。

本文件把 #7 里的「画面设置」（`OSDConfig` + `FrameMirror` + `PictureMask`）展开成可实现形态。
**不含**录像计划（另一议题）。

## 1. 用户任务

| 任务 | 触发场景 | 用户期望 |
| --- | --- | --- |
| 遮挡不该看的区域 | 隐私合规：对着邻居窗、马路、工位 | 画一下就好，位置能反复调 |
| 把画面摆正 | 装反了 / 装倒了 | 点一下，立刻在画面上看到 |
| 在画面上烧信息 | 时间戳、点位名 | 对齐位置，看清字号 |

三件事的共同点：**都在描述「画面上的位置或方向」**。所以操作应当发生在画面上。

## 2. 设计主张

> 画面上的事，画在画面上做；数值是它的二级表示，不是唯一表示。

三条原则：

1. **一屏一任务** —— 镜像 / 遮挡 / OSD 是同一件事（这一路码流的画面长什么样），合并为一个工作区，不用 tab 切组。三组共 14 个字段，一屏可容。
2. **事实与草稿分离** —— 设备值 / 我的改动 / 待下发差异各有落点；**没有事实就不给编辑**。
3. **编辑在画面，提交按类型** —— 交互层合一屏，下发仍按 `ConfigType` 分块（协议要求），结果由回读对账收敛。

## 3. 现状问题清单

### P0-1 读路径整体 400，该功能从未可用（阻断级）

**证据（可复现）**

- `server/resource/logs/` 全部日志中，`route=/api/gb28181/device-mgmt/channel/:id/device-configs` `method=GET` 共 **46 次，46 次 `http_status=400`，0 次 200**，响应体恒为 **68 字节**（`response_bytes=68` × 46）。
- 同一时段同路由族 `.../video-params` 为 **98 次 200**、`.../channels` 全 200。→ 通道 / 目标 / 鉴权链路正常，问题只在这一条路由上。
- 68 字节恰好等于 `{"code":1,"message":"未知的配置类型: basicParam","data":null}`。逐一核对其余候选文案的体积：`未知的配置类型: alarmReport` = 69、`PTZ Service 未就绪` = 56、`未选择通道，无法读取设备配置。` = 80 —— 只有 `basicParam` 那条落在 68。

**根因（两处字符串大小写不一致）**

| 位置 | 取值 |
| --- | --- |
| `web/src/views/gb28181/device-mgmt/deviceConfigGroups.ts`（`basic` 组 `configTypes`） | `"basicParam"` |
| 同上（`alarm-report` 组） | `"alarmReport"` |
| `server/app/gb28181/manscdp/video_param.go:35` `ConfigTypeBasicParam` | `"BasicParam"` |
| `server/app/gb28181/manscdp/video_param.go:46` `ConfigTypeAlarmReport` | `"AlarmReport"` |
| `server/app/gb28181/controllers/device_config.go:276` | 不匹配即 `未知的配置类型: X` → 400 |

⛔ **这是把「协议 JSON 键名」当「标准 ConfigType 名」用了。** 两者在本仓是刻意区分的两样东西：

- **JSON 键名** = `manscdp.DeviceConfigBlocks` 结构上的 json tag（小驼峰：`basicParam` / `alarmReport` / `osdConfig`…）
- **ConfigType 名** = 标准原文的元素名（首字母大写：`BasicParam` / `AlarmReport` / `OSDConfig`…）

前端**下发**用的 `blocks` 键必须是小驼峰（现有实现是对的，见 `deviceConfigPayload.ts:502`）；
**读接口**的 `configTypes` 参数必须是标准名（写错了）。

**影响半径被并集放大**

```ts
const FAMILY_CONFIG_TYPES = Array.from(new Set(CONFIG_GROUPS.flatMap(group => group.configTypes)));
```

这是**所有组的并集**，所以一个字符串写错 → 整个 GET 400 → 不是「设备维护那一组读不了」，
而是 **画面设置 / 录像存储 / 报警控制 / 设备维护 四个 tab 全部读不了**。

**连带后果（比 400 本身更值得修）**

- 读失败时 `familyEntries` 为空 → `familyBaseline` 停留在空白模板 → 用户看到的
  「画面镜像 = 不启用镜像」「遮挡区全 0」**不是设备值**，是空白模板。
- 界面上没有任何地方说明这件事。
- 用户改任一项 → `activeDirtyCount` 从 0 变 1 → **下发按钮亮起** → 用户在没有任何设备事实的情况下**盲写**。

**为什么没被拦住**

- 前端 `DeviceConfigDrawer.test.ts:179` 断言 `options.configTypes` 等于
  `CONFIG_GROUPS.flatMap(g => g.configTypes)` —— **拿同一个常量和自己比**，恒真，永远抓不到值写错。
- 后端没有覆盖 `requestedDeviceConfigTypes` 的用例。
- 契约两侧都没有「前端字符串 ∈ 后端 `ConfigTypeOrder`」的锚点。

**修法**：2 处字符串（`"BasicParam"` / `"AlarmReport"`），并补一条锚点测试 ——
前端 `CONFIG_GROUPS.flatMap(g => g.configTypes)` 的每个值都必须出现在一份与后端
`ConfigTypeOrder` 同源的清单里，否则就是回到「两份定义各自漂」。

### P0-2 未回读时字段仍可编辑，且用空白模板冒充设备值

- 现状：读取没成功也允许改。`familyFieldsDisabled` 只挡 loading / applying / 无权限 / 非 ready。
- 违反 spec「未返回、未知、不支持、离线、无权限、过期、失败分别表达；未知不伪装成关闭或数值零」。
- 设计：未回读 → 字段禁用 + 显示「—」+ 状态条明说「尚未读取设备值」。

### P0-3 错误文案是传输层原文

- 现状：`DeviceConfigDrawer.vue` 的 `loadDeviceConfigs` catch 后取 `(error as Error)?.message`
  → 屏幕上就是 `Request failed with status code 400`。
- 设计：透出后端业务消息；并把「请求没发出去」「设备没响应」「设备接受了但值没变」「设备不认识这一项」分开。

### P1-1 遮挡区 = 8 个手输像素输入框

- 用户想的是「把画面右下角那块挡掉」，界面要求的是两个角点的绝对坐标。
- 没有画面预览，输错了只能靠「下发 → 回读 → 人眼比对」闭环发现。
- 「四个坐标全 0 视为未启用、不下发」这条语义藏在数字里。

### P1-2 画面镜像 = 文字下拉框

- `deviceConfigGroups.ts:181` 注释已明确警告：**1 = 水平、2 = 上下**，
  「写反的后果是下发上下翻转、画面左右翻，回读对账还会显示一致（因为对账比的是值，不是画面对不对），只能靠人眼发现」。
- 文字下拉把一件**天然是图形**的事压成字符串 —— 应图标化。
- 现文案「中心镜像（上下左右同时翻转）」也不准确：那是旋转 180°，「上下左右同时翻转」描述的是过程不是结果。

### P2-1 入口重复

- 侧栏顶部有组切换（`dcg-nav`，渲染成 4 列 grid 只装 2 个按钮）。
- 底部「快捷操作」卡片又有一份**同样的 2 个按钮**（`linked-deviceconfig-actions`），文案「当前 / 切换」。
- spec 产品要求「同一个配置项只有一个权威编辑入口；快捷入口定位到同一份编辑内容」——
  现在两份入口做的是同一件事（切组），纯冗余。

### P2-2 没有差异视图

- 只有 footer 一个「待下发 N 项」数字，看不到改了哪几项、从什么改到什么。
- 「还原」是整组还原，没有单项撤销。

## 4. 交互详设

### 4.1 布局：编辑层叠在主视频上，属性在侧栏

依据 spec「保留视频上下文」+「复杂配置要有足够编辑空间，不将所有字段强塞入狭窄侧栏」。

- 播放控制台的**主视频上加一层编辑叠加层**（工具栏可开关）
- 侧栏「画面设置」承载属性与提交
- **不新开弹窗**（spec：不再用入口按钮启动另一套配置弹窗）

侧栏自上而下：① 状态条 → ② 画面镜像 → ③ 隐私遮挡 → ④ 图像叠加 OSD → ⑤ 提交区。

### 4.2 画面镜像

- 4 个**图标按钮**：原图 / 左右 ↔ / 上下 ↕ / 中心 ⤢
- 点选后主视频**本地立即预览**（CSS transform），不等下发
- 下发映射沿用现有取值：原图 = 0，左右 = 1，上下 = 2，中心 = 3（`MIRROR_OPTIONS` 不动）
- ⛔ 图标不能**替代**文字：对账比的是值不是画面对不对，所以每个按钮保留文字副标题
- 未回读时四个按钮禁用

### 4.3 隐私遮挡

- 主视频上叠加可拖拽 / 可缩放的矩形，上限 4（`MAX_MASK_REGIONS`）
- 每个矩形：左上角编号角标、右上角删除、四角缩放把手
- **坐标口径保持标准原义**：两个角点（左X, 左Y, 右X, 右Y），**不是**位置 + 宽高
  - ⛔ `deviceConfigGroups.ts:74` 已警告：按「左上角 + 宽高」理解会画出**偏移一整个宽高的假遮挡**，而两侧都不报错
  - 因此拖拽的内部实现必须显式在「角点空间」做运算，不要中途换成宽高再换回来
- **空白 = 不下发**：不创建区域就是不下发，与标准「四个坐标全 0 视为未启用」等价，但不再要求用户理解它
- 侧栏每个区域一行：编号 + 坐标摘要 + 「精确数值 ▾」
  - 展开后才是 4 个像素输入框（spec：保留精确数值），**默认收起**
- 总闸「启用遮挡」保留，但必须能表达「有区域、总闸关」这个不一致态：
  - 该行标注「已画好，总闸未开，不会生效」
- 画面上标注分辨率与码流（来源：已回读的 `VideoParamAttribute`，或目录 `StreamNumberList`），
  拖拽时实时显示换算后的像素值 → 消除「要跨面板抄分辨率」的前置知识

### 4.4 图像叠加 OSD

- 时间戳 / 文字在画面上是**可拖拽的框**，拖动改 X/Y；「窗口长度 / 宽度」用右下角把手改
- 时间格式：从「名字」改成「样例单选」
  - 选项直接渲染成当前时刻的实例：`2026-09-19 15:15:17` / `2026年09月19日15时15分17秒`
  - **必须保留**「不指定（不下发该元素）」这一项 —— 它是「不发」，与「发一个空格式」是两件事
- 叠加文字（最多 8 条、每条 ≤ 32 字符）：画面上逐条添加、就地编辑，字符数校验就地提示
  - ⛔ 上限口径是**字符**不是字节（`MAX_OSD_TEXT_LENGTH` 注释：中文按 1 个算），提示文案不要写成「字节」

### 4.5 状态与提交

状态四态与后端 reconcile 一一对应，**不新造词**：

| 界面状态 | 后端 reconcile | 界面表现 |
| --- | --- | --- |
| 尚未读取设备值 | `never_read` | 灰点；字段禁用并显示「—」 |
| 正在读取… | `pending` | 灰点 + 进度；字段禁用 |
| 已同步 · 回读于 HH:MM | `read_ok` | 绿点；可编辑 |
| 设备未返回此配置 | `type_absent` | 灰点；说明「多半是该设备不认识这一项」，**不是失败，也不是零** |
| 设备已接受但值未生效 | `mismatch` | 黄点；附设备错误码 |
| 读取或下发失败 | `failed` | 红点；透出业务消息 |

提交：

- 按钮收敛为 `应用 N 项`（主）+ `撤销`（次）
- 「读取」从平级按钮**降为状态条上的刷新图标** —— 它是「重新取事实」，不是「完成一次操作」
  - 入口必须保留：spec 要求配置以设备回读核对提交结果
- **差异抽屉**：点状态条上 `N 项未下发 ▾` 展开，逐项「配置项 / 设备当前值 / 将下发」三列 + 单项撤销
  - ⛔ 撤销单项 ≠ 设备恢复出厂（spec 明确要区分）
- 应用后自动回读对账（后端已实现 `reconcilePending` + 自动排队 ConfigDownload），结果直接回状态条
  - ⛔ 界面**不得**把 POST 200 当成功终态（后端注释：写入应答只有 `Result`、没有回显）
- 读取遇到未下发草稿：**不静默覆盖**，问「保留我的改动 / 改用设备值」

### 4.6 错误呈现

| 类 | 例子 | 界面 |
| --- | --- | --- |
| 请求没发出去 | 通道离线、无权限 | 红点 + 具体原因 |
| 请求发了、设备没响应 | 超时 | 黄点 +「已发送，设备未应答」+ 重试 |
| 请求发了、设备接受、值没变 | `mismatch` | 黄点 + 设备错误码 |
| 设备不认识这一项 | `type_absent` | 灰点 +「该设备未返回此配置」 |

⛔ 一律不出现 `Request failed with status code 400` 这类传输层文案。

## 5. 数据口径（前端实现须遵守）

- `familyValues` / `familyBaseline` 现有语义**保留**：基准 = **最近一次回读值**，不是打开面板时的快照。
  理由：下发后设备可能被别的网管改掉，拿旧快照当基准会把「设备已经不同了」算成「用户没改」。
- 新增：草稿需能表达「是否曾经回读过」。`never_read` 时**不得**把默认值当基准参与脏值统计。
- 切组 / 切通道 / 关闭时保护草稿（spec 明确要求）。
  ⛔ 现有代码在切通道时**重置全部表单**（`DeviceConfigDrawer.vue` 的 `watch(props.channelId)`），需改为「有未下发草稿时先提示」。

## 6. 非目标

- 不改 `VideoParamAttribute`（视频编码）通道
- 不改后端 ConfigType 词汇表；本设计不新增 ConfigType
- 不引入 ONVIF / 厂商私有参数（镜像是标准 `FrameMirror`，不是 ISP 参数）
- 不做 2016 降级形态：`FrameMirror` / `PictureMask` 均为 2022 新增，
  2016 设备的正确表现是回读 `type_absent` 后灰态说明

### 7.2 第二轮：底栏卡片化（2026-09-19）

**设计修正**（用户当场纠正，我此前的主张作废）：

- ⛔ 不是「把画面处理搬到别处」，而是**把功能拆成并列卡片、平铺摆出来**。底部工作区的语义是
  **卡片容器**，不是「N 个同类对象的集合」——我先前那条「镜像没有列表语义所以不该进底栏」
  的反对意见前提就错了，作废。
- ⛔ **2016 设备不加门禁**：下发就下发，失败让用户看见。此前主张的「灰态 + 说明」作废。
- ⛔ **没有多分屏场景**，一律单屏操作，编辑层归属问题不存在。

**落地形态**（三张卡并排，与云台底栏同一套栅格）

| 卡 | 内容 |
| --- | --- |
| ① 画面遮挡 `picture-mask-card` | 「启用遮挡」总闸 + 4 个槽位（`#序 · 左X,左Y → 右X,右Y`）+ 删除 + 「读取 / 新建」 |
| ② 画面镜像 `picture-mirror-card` | 4 个方向按钮（原图 / 左右 / 上下 / 旋转 180°），图标 + 文字副标题 |
| ③ 提交 `picture-apply-card` | 「待下发 N 项」+ 坐标口径（`坐标基于 1280×720`）+ 还原 / 下发 |

**三处关键机制**

1. **卡片不是第二份状态**：`DeviceConfigDrawer` 用 `defineExpose` 暴露画面组读写口
   （`pictureRegions` / `setPictureRegion` / `setPictureMirror` / `applyPictureGroup` …），
   读写的就是 `familyValues.picture`，脏值统计、下发、回读对账全部复用同一套。
   ⛔ 判据必须按 `picture` 组算，不能复用 `activeGroup`（侧栏此刻可能停在别的组）。
2. **坐标参考系 = 播放器解码尺寸**：`PlayWindow.vue` 暴露 `getVideoSize()` 并每秒广播
   `videosize`。⛔ 不能订阅库的 `videoInfo` 事件（emit 被 `!this.init` 守卫，只触发一次），
   所以由我们主动轮询。框选比例 × 解码尺寸 = 下发的像素坐标。
3. **画完自动开总闸、没拿到尺寸就不给画**：前者避免「画了却没生效」，后者避免拿错口径的
   坐标写进草稿（`finishMaskDraw` 会拒绝并提示）。

**验证**

- `PlayConsoleLinked.test.ts` 新增 4 条且全过：遮挡槽位按 `Seq` 渲染 / 镜像按回读值高亮 /
  **框选换算**（(10,20)-(110,80) ÷ 200×100 × 1280×720 = `64,144 → 704,576`）/
  下发带 `frameMirror` + `pictureMask` 两块且 `Seq` 用槽位编号。
- 框选用例特意 mock 了 `getBoundingClientRect`：jsdom 里它恒为 0，不 mock 的话坐标会被
  clamp 到边界，断言退化成恒真。
- 合并跑 `device-mgmt/` + `PlayConsoleLinked.test.ts`：**408 passed / 7 failed**，
  7 条失败与改动前**逐条一致**（即 §7.1 记录的既存 WIP 脱节），本轮**未新增失败**。

**一条待定**：`Seq` 要不要重排。⛔ **标准并未要求 `Seq` 连续**（原文只写「取值范围 1～4」，
我早先记的「且连续」已作废）。当前按**槽位编号**发（`mask3` → `Seq=3`），删掉中间区域后序列
稀疏 —— 这是保真做法；若某些设备要求连续，需在真机上验证后再定。

### 10.3 另一条独立故障：`gb_ptz_operation` 的 ABBA 死锁（1213）

后端 WARN `设备配置应答处理失败 … code=1213`，而**数据其实落库成功了** ——
表现为"值读到了、操作行状态却漂到 `timeout`"。根因是**锁序倒置**（`SHOW ENGINE INNODB STATUS`
的 `LATEST DETECTED DEADLOCK` 有完整快照）：**状态收割器**走
`idx_ptz_operation_status_deadline` 再加 PRIMARY，**应答处理器**走 PRIMARY 再加二级索引
（它也改 `status`），InnoDB 回滚后者。

⭐ **不是偶发**：两者判据正好互补（`deadline_at <= now` vs `> now`），
**截止时刻前后几百毫秒内必然同时命中同一行**。
修法方向（未实施）：收割器加秒级宽限窗 / 应答落库加 1213 有界重试 / 治本让两条写路径锁序一致。
这与 10.2 的 P0 是**两件事**，不要合并归因。

## 11. 第三轮提案：下发流程重设计（2026-09-19，**待拍板**）

### 11.1 先归因：用户给的方案（弹窗 / 悬浮）都对，但没打到根因

现象是「画完还要跑到右下角点下发，容易忽略」。但**"容易忽略"不是因为按钮难找**，
而是三层问题叠加：

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **状态不可见**（真因） | 画完的区域在画面上已经是**实心黑块**的样子，看起来"已经生效"，实际只是本地草稿。用户**无法从画面上分辨生效没有** —— 所以不是"没看见提交按钮"，是**不知道还有事没做完**。 |
| 2 | **空间割裂** | 动作（框选）在画布上，确认（下发）在面板右下角，相距一屏，视线要跳。 |
| 3 | **确认时机错位** | 协议上 `pictureMaskCfgType` 是 **`SumNum` + `RegionList` 整块替换**下发 ⇒ **不能边画边发**，必须"攒完一次性下发"。但交互把它拆成了"画一块 → 去别处提交"。 |

### 11.2 三层方案

**第 1 层（必做，成本最低、价值最高）：草稿态与生效态在画面上长得不一样**

- 已下发（生效）：**实心纯黑块**
- 未下发（草稿）：**虚线框 + 半透明底 + 角标「待下发」**

这一条直接消除"以为已经生效"的错觉，是解决"容易忽略"的**主力手段**，不是锦上添花。

**第 2 层（必做）：把提交从"卡片"搬到"画布上的浮条"**

- **位置**：画布内**底部居中**（⛔ 不用右下角：右上有存储卡、右下有缩略图/控件，底部居中视线最顺）
- **出现条件**：**仅当 `pictureDirtyCount > 0` 时出现**，无变更时完全消失、不占位
- **内容**：`遮挡 2 处待下发` ＋ `[下发]` ＋ `[再画一块]` ＋ `[撤销]`
- **提交后三态**：`下发中…`（设备回读需 1~2s）→ 成功后浮条消失；**失败留在原地并显示原因**，
  ⛔ 不许静默消失
- ⛔ **为什么不用 dialog**：遮挡最多 4 块，用户常在几十秒内**连画 2~4 次**。每画一块弹一次窗
  = 连弹 4 次，用户会烦到条件反射关掉、反而更容易漏。浮条是**常驻可见、不打断节奏**。

**第 3 层（可选）：dialog 只用在"离开时兜底"**

- **时机**：有未下发变更时，用户**切通道 / 切页签 / 关面板**
- **文案**：`遮挡有 2 处未下发，离开后本次绘制将丢失。[下发并离开] [直接离开] [留在本页]`
- 这是**低频**场景（一次操作最多触发一次），才是弹窗的合理位置。

### 11.3 明确排除的方案

⛔ **「边画边下发」（画完一块立即下发）不可行** —— 协议上是**整块替换**：
每次下发都带 `SumNum` + `RegionList`，逐块发会**互相覆盖**。除非每次重发全部已画区域
（发 1 块 → 发 2 块 → 发 3 块…），那是 N 次冗余下发、且中间态混乱。**不做。**

### 11.4 干掉提交卡之后，空出的卡位怎么用

- 底栏从 3 张 → **2 张**（遮挡卡 + 镜像卡），空出 1~2 个位。
- ⛔ **不要**把空位填成「草稿汇总卡」—— 那是**另一个提交框**，等于把问题换个地方重演。
- **职责重新划分**：
  - **遮挡卡** = 管理（列表 / 删除 / 总闸 / 回读刷新）
  - **画布浮条** = 操作（新建 / 框选 / 提交 / 撤销）
- 空出的卡位留给后续（用户提过 OSD 第四张卡，本轮已定"留侧栏"，腾出空间后可重议）。

### 11.5 两个必须处理的细节

1. **总闸（`On`）与区域的关系**：`On=0` 时区域不生效。当前实现是"画完顺带开总闸"，
   浮条文案要**显式说明**：`2 处待下发（将同时开启遮挡）`，别让用户事后发现"画了但没生效"。
2. **`On` 是标准必选字段、没有独立"启用/停用命令"**（A.2.1.17 原文「画面遮挡开关，
   取值0-关闭，1-打开（必选）」）。所以"停用"= 下发一次 `On=0`，UI 上就是一个开关，
   ⛔ 不要设计成两条独立操作。
