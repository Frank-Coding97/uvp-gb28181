# 播放控制台 用户体验架构重构设计

## 0. 本文件的位置

上游 `docs/device-workbench-refactor-spec.md:93` 把「具体布局」**显式留白**：

> 产品载体建议：工作台内提供可扩展的配置编辑空间，保持直接内嵌；**具体布局在 plan 阶段结合对标和原型确定**。

本文件补的就是这一层。四件事：

1. **信息架构** —— 8 个页签该怎么分（现在分错了）
2. **空间架构** —— 每个区域该负责什么、哪些东西必须常驻（现在职责随页签漂移）
3. **交互流程** —— 「操作 → 确认」怎么闭环（现在跨三个区域）
4. **状态语言** —— 全页统一的词汇表（现在十几套）

「画面遮挡」模块的交互已在 `docs/picture-settings-design.md` 定稿并落地。本文件把它**当作设计母版**，先拆出它为什么好，再抽成全页规则。

---

## 1. 先回答：为什么「画面遮挡」那套感觉好

要复用它，得先分清那是「运气好」还是「机制对」。拆开看是四条机制：

| # | 机制 | 母版里的出处 |
| --- | --- | --- |
| **M1** | **动作在画面、管理在面板** —— 卡片只留「列表 / 删除 / 总闸 / 回读」，新建 / 框选 / 提交 / 撤销全在画布上 | `picture-settings-design.md` §11.4 |
| **M2** | **草稿与事实长得不一样，且差别出现在动作发生的地方** —— 已生效 = 实心黑块；未下发 = 虚线框 + 半透明底 + 角标「待下发」 | §11.2 第 1 层 |
| **M3** | **确认就近、有变更才出现、不打断节奏、不静默消失** —— 浮条贴画布底部居中，`dirty=0` 时完全消失不占位，失败留在原地显示原因 | §11.2 第 2 层 |
| **M4** | **数值是二级表示；没有事实不给编辑；状态词不新造** | §4.3 / §4.5 |

其中 **M2 是主力**。母版自己归因得很准（§11.1）：

> 真因不是「没看见提交按钮」，而是**不知道还有事没做完** —— 画完的区域在画面上已经是实心黑块的样子，看起来「已经生效」，实际只是本地草稿。

这三条机制是**可移植的**：它们不依赖「遮挡」这个业务，只依赖「有草稿、要下发、靠回读对账」这个共同形状 —— 而这恰好是**整个设备配置族的形状**。

## 2. 现状诊断

主载体：`web/src/views/gb28181/components/PlayConsoleLinked.vue`（11422 行）。下文行号均指该文件（`DeviceConfigDrawer.vue` 简写 **D**）。

### 2.1 四条结构性根因

#### 根因 A：页签是一个「会同时换掉三个区域」的模式开关

`activeTab` 一处状态，同时驱动四个东西：

| 被驱动的东西 | 证据 |
| --- | --- |
| 右栏内容 | `activeConfigGroups`（L405–416）→ `DeviceConfigDrawer` 的 `groupKeys`（L6366） |
| 底栏内容 | 5 套 `.linked-detail` 的 `v-show`：ptz L4932 / deviceconfig L5380 / probe L5532 / advanced L5689 / videoparam L5792 |
| 画布叠加层 | 浮条 + 框选**仅** `activeTab === 'deviceconfig'` 时可用（L4163–4165） |
| 左侧页签轨 | 页签可见性门禁（L429–438） |

**后果一**：用户的意图可能只是「我要改录像计划」，但一次点击导致右栏整块换、底栏整条换、画布上的草稿入口消失。这是**一次动作触发三处非预期变化**。

**后果二（几何跳变）**：`record` / `alarm` / `device` 三个页签**没有对应的 `.linked-detail` 块**，而底栏的定高 148px 写在 `.linked-detail` 上（L8009/L8026）→ 切到这三个页签时**页脚整条塌掉 148px**，画布与右栏随之重排。

**后果三（位置漂移）**：底栏注释 L8135–8137 明说定高 148 是「为了切页签时卡片位置不跳」，但 5 套布局的**卡片数量不同**（云台 4 张 / 画面 2 张 / 探针 3 张 / 高级 2 张 / 视频编码 1 张）—— 定高只解决了「高度不跳」，没解决「卡片位置不跳」。

#### 根因 B：**「改设备配置」这一件事，被切成了 5 个并列页签**

`CONFIG_GROUPS`（`deviceConfigGroups.ts:231`）定义了 7 个配置组。而侧栏的 5 个页签只是把其中 6 个切成片：

| 页签 | 承载的组（`configWorkspaceGroups` L405–414） |
| --- | --- |
| 画面设置 `deviceconfig` | `["osd"]` |
| 视频编码 `videoparam` | `["video-param"]`（L6345，独立传参） |
| 录像存储 `record` | `["record-plan", "alarm-record"]` |
| 报警控制 `alarm` | `["alarm-report"]` |
| 设备维护 `device` | `["basic"]` |

**5 个页签渲染的是同一个 `DeviceConfigDrawer` 组件**（L6341 与 L6361），只是 `groupKeys` 不同。

也就是说：**页签层与配置组层是完全冗余的两层**，而组导航 `dcg-nav` **早就实现了**（D:1596，`configGroups.length > 1` 才渲染）—— 它现在隐藏，仅仅因为「每组恰好一个页签」。

> ⚠️ 这直接违反上游 spec 的产品要求第 1 条：
> 「**同一个配置项只有一个权威编辑入口；快捷入口定位到同一份编辑内容**。」
> 现在同一个配置组有**一个页签 + 一份组导航 + 一张底栏卡**三个入口层。

**而且这件事的项目自己已经做过一次**：§7.1 第 9 步「撤掉『画面设置』的二级 tab … `dcg-nav` 因只剩一组而自动隐藏 —— 不是『藏起来』，是这一层不再需要」。**同样的动作没有推广到另外 4 个页签。**

#### 根因 C：「配置」被劈成两半，中间隔着一次视线跳

以视频编码为例，一次完整的「读取 → 修改 → 下发」要横穿两个区域：

```
① 点「读取」—— 在【底栏】右卡           L5813  video-param-bottom-read
② 字段出现 —— 在【右栏】DeviceConfigDrawer
③ 点「下发」—— 回到【底栏】右卡           L5824  video-param-bottom-apply
```

而且**同一屏上有两份完全同名的按钮**：

| 位置 | 读取 | 还原 | 下发 |
| --- | --- | --- | --- |
| 底栏卡（L5800–5832） | `video-param-bottom-read` | `video-param-bottom-reset` | `video-param-bottom-apply` |
| 内嵌抽屉（D:1634–1665） | `dcg-read` | `dcg-reset` | `dcg-apply` |

底栏那三颗按钮的实现就是转调抽屉的方法（`@click="videoConfigRef?.read()"`）—— **两套 UI 驱动同一份状态**。

更说明问题的是底栏空态文案（L5867–5869）：

> 写的是「**先在右侧点『读取设备参数』**」，而读取按钮实际在**底栏**。

文案与实现指了两个不同的方向 —— 说明这个劈裂连作者自己都会记混。这不是措辞问题，是**结构本身在制造歧义**。

#### 根因 D：状态语言有十几套，各自为政

| 形态 | 表达什么 |
| --- | --- |
| `.session-badge` 会话胶囊 | 会话生命周期（8 态） |
| `.tab-draft-dot` 页签角标 | 未下发草稿（跨页签） |
| `.picture-draft-bar` 浮条 | 画面草稿 + 提交 |
| `.picture-card-error` / `.picture-card-notice` | 错误 vs 「发出去了但结果不同」 |
| `.cruise-running-chip` / `.scan-running-chip` | 「指令已发出」（非「运行中」） |
| `.cruise-status-badge` | 未验证 / 可试运行 / 可调用 / 已禁用 |
| `.home-config.state-{tone}` | 看守位 10 态 |
| `.probe-status` 状态点 | 探针（等待/采样中/完成） |
| `.snapshot-status` | 抓拍（接收中 x/y、已完成 x/y） |
| `advancedOperationStatus[...]` 小字 | 每按钮下方「以设备应答为准」 |
| `capabilityActionTitle()` tooltip | 设备支持情况 |
| `Message.*` Toast | 50+ 处 |

**用户每碰一个功能就要学一种「这块现在到底怎么了」的读法。** 而遮挡那套之所以好，是因为它在**一个功能内部**建立了一套统一的「事实 / 草稿 / 结果」语言（M2 + M4）—— 但那套语言**没有变成全页词汇**。

## 3. 设计语言（全页规则）

把 §1 的母版机制反推成**六条可执行的规则**。后面所有改法都能追溯到这六条之一。

| # | 规则 | 来自 |
| --- | --- | --- |
| **R1** | **画面上的事，在画面上做。** 凡描述「画面/设备的位置或方向」的操作（遮挡、镜像、OSD 落点、3D 放大框、云台转向），动作发生在画布上；面板只做管理与回读。数值输入是二级表示，默认收起。 | M1 + M4 |
| **R2** | **草稿与事实必须在动作发生的地方长得不一样。** 已生效 / 未下发 / 结果未知，三者在**同一个坐标系里**用颜色 + 线型 + 文字三重区分（色弱可辨）。 | M2 |
| **R3** | **确认贴着动作，有变更才出现，不打断节奏，不静默消失。** 悬浮条优先；弹窗只用于「离开兜底」与「危险动作」。 | M3 |
| **R4** | **没有事实就不给编辑。** 未回读 → 字段禁用 + 显示「—」+ 状态条明说原因。 | M4 |
| **R5** | **区域职责固定，不随任务变。** 一个区域在整页生命周期里只负责一类事。 | 新（治根因 A） |
| **R6** | **状态词表不新造，与后端 reconcile 一一对应。** 全页只保留一套状态词汇。 | M4 |

> ⛔ **R5 是本次新增的一条**，也是母版没覆盖到的部分 —— 母版只解决了「一个功能内部」的秩序，没解决「功能之间」的秩序。根因 A 正是「功能之间」的问题。

## 4. 新架构

### 4.1 信息架构

**8 个页签 → 3 个任务分组。**

判据用**行为形状**，不用协议族（spec 产品要求：「按用户任务组织功能，协议族和标准条款用于技术详情」）：

| 分组 | 行为形状 | 内容 | 由谁构成 |
| --- | --- | --- | --- |
| **① 实时操作** `live` | **点一下发一条，发完就完**；无草稿、无回读对账 | 云台与镜头 · 对讲 · 预置位调用 · 巡航启停 · 看守位 · 自动扫描 · 3D 放大 · 抓拍 · 布防撤防 · 报警复位 | `ptz` + `advanced` 的命令侧 |
| **② 设备配置** `config` | **读 → 改 → 下发 → 回读对账**；有草稿、有事实、有结果 | `CONFIG_GROUPS` 的 7 个组：视频参数属性 · 图像叠加 OSD · 画面处理 · 录像计划 · 报警录像 · 基础参数 · 报警上报 | `deviceconfig` + `videoparam` + `record` + `alarm` + `device` |
| **③ 诊断** `diagnose` | **只读观测**，无编辑 | 流信息 · 逐帧健康检测 · 帧到达时间线 | `probe` |

三个分组的关键性质：

- **只有「设备配置」有草稿与提交** —— 于是「草稿状态条 / 浮条」这类组件只需在一处设计，不用为 8 个页签各想一套。
- **危险动作**（重启 / 设备升级 / 格式化 / 报警复位）留在「实时操作」内，作为**独立卡 + 二次确认**（spec 产品要求：「重启、格式化、升级、可能中断接入的基础参数修改说明影响并确认」）。
- 「设备配置」的 **7 个组用组导航承载**（`dcg-nav` 已实现），**不再用页签**。这一步使得 spec 产品要求第 1 条「唯一权威编辑入口」成立。

### 4.2 空间架构

**核心改动：三个区域的职责写死，且画布与工作坞常驻。**

```
┌──────────────────────────────────────────────────────────────────┐
│ 标题栏  通道身份 · 会话状态 · 窗口控制                    （不变） │
├────────┬────────────────────────────────────┬────────────────────┤
│        │                                    │                    │
│ 任务   │   画布【常驻，任何分组下都在】       │  属性栏            │
│ 分组   │   ┌──────────────────────────────┐ │  = 当前分组的       │
│        │   │  视频                         │ │    编辑面          │
│ ① 操作 │   │  · 框选层 / 拖拽层（按需出现） │ │                    │
│ ② 配置 │   │  · 草稿与生效的三重区分        │ │ ┌────────────────┐ │
│ ③ 诊断 │   │  ──────────────────────────── │ │ │ 组导航（配置时） │ │
│        │   │  ⚡ 就地浮条（有变更才出现）    │ │ ├────────────────┤ │
│        │   └──────────────────────────────┘ │ │ 字段 / 卡片      │ │
│        │                                    │ ├────────────────┤ │
│        │                                    │ │ 读取 还原 下发   │ │← 提交贴字段
│        │                                    │ │   （唯一一份）    │ │
├────────┴────────────────────────────────────┴────────────────────┤
│ 工作坞【常驻定高】：即时操作卡（可折叠）+ 常驻状态条                │
└──────────────────────────────────────────────────────────────────┘
```

**四条职责规则**：

| 区域 | 固定职责 | 治哪个断点 |
| --- | --- | --- |
| **画布** | 现场。画面类操作（框选 / 拖拽 / 3D 放大）+ 草稿标记 + 就地浮条。**任何分组下都可用。** | B4、B8 |
| **工作坞** | **只放「即时操作」**。高度恒定、卡位恒定。 | B4、B5 |
| **属性栏** | **当前分组唯一的编辑面**，含它自己的读取 / 还原 / 下发。配置分组时顶部带组导航。 | B1、B2、B3 |
| **弹窗** | 只用于**离开兜底**与**危险动作二次确认**。 | B7 |

**三个具体动作**：

1. **画布常驻** —— 把浮条与框选层的 `v-if="activeTab === 'deviceconfig'"`（L4163）去掉。理由：画布是这个产品唯一的「现场」，其他一切都是围绕它的远程操作；把它锁在一个页签里没有依据。
2. **工作坞 = 常驻即时操作坞**（推荐，见 §7 待拍板）—— 即时卡永远在同样坐标，高度恒定 → 几何与位置都不跳；且在做配置时天然需要「先把云台转过去看一眼」。折叠态保留一条定高状态条，避免噪音。
3. **提交条收到属性栏底部** —— 删除底栏那一份重复的读取 / 还原 / 下发（L5800–5832）与整张「参数对照卡」的按钮组，只保留 D:1634–1665 那一份（就近字段）。

### 4.3 画面类配置的归位

遮挡 / 镜像 / OSD 三者在协议上同属「描述画面」的配置族，在交互上也应同构。现状是**三者处置各不相同**：

| 组 | 现状落点 | 目标落点 |
| --- | --- | --- |
| 画面处理 `picture`（遮挡 + 镜像） | 底栏两张卡（L5386 / L5497） | 属性栏「配置」分组的 `picture` 组（**管理**）+ 画布（**操作**） |
| 图像叠加 OSD `osd` | 右栏表单（§7.1 第 7 步未做） | 同上，`osd` 组 |

关键：**`CONFIG_GROUPS` 里本来就有 `picture` 组**（`deviceConfigGroups.ts:291`「画面处理」），只是被摘出了侧栏（`configWorkspaceGroups` 不含 `picture`）。把它放回去，组导航就完整覆盖 7 组。

而画面上的操作**完全沿用母版**：框选层、草稿/生效三重区分、就地浮条、坐标基准注脚、精确数值折叠 —— 一行都不用重设计。

> ⚠️ 这一步**推翻了 `picture-settings-design.md` §7.2 第二轮的一个决定**（用户当时要求「把功能拆成并列卡片平铺在底栏」）。所以它是 §7 的待拍板项，不是既成结论。两者可以并存：**卡片留在坞、或卡片归位到组**，取哪个取决于「坞要不要纯化为常驻即时操作坞」。

### 4.4 交互流程重设计

逐条对照 §2.2 的断点。

**流程 1：改一条设备配置（治 B1 / B2 / B3）**

| | 现状 | 改后 |
| --- | --- | --- |
| 找入口 | 在 5 个页签里猜「录像计划在哪」 | 进「设备配置」→ 组导航里直接点「录像计划」 |
| 读 | 底栏点「读取」 | 属性栏底部点「读取」（贴字段） |
| 改 | 右栏字段 | 同一处 |
| 下发 | 回底栏点「下发」 | 原地点「下发」 |
| 结果 | 底栏「N 项未下发」｜卡片 error/notice | 就地状态条 + 差异清单（点 `N 项 ▾` 展开） |

**流程 2：设自动扫描边界（治 B6）**

现状：右栏摇杆把云台转到位（L5905）→ 视线下移到**底栏最右卡**（L5327/L5336），跨整个画布高。
改后：边界按钮**贴到摇杆旁**（同一属性栏区域内）。理由：这是**同一次操作的两个步骤**，被拆到了对角。
附带：`设左边界` 与 `设右边界` 各需一次云台定位，所以属性栏里应呈现为「① 转到位置 → ② 记下」的两步条，而不是两个孤立按钮（现状靠提示文案 L5369–5371 说明）。

**流程 3：新建预置位 / 巡航（治 B7）**

现状：底栏卡「添加」→ 居中弹窗（380/480）填表 → 提交。**表单遮住画面**，而用户要填的恰恰是「刚才画面的那个位置叫什么」。
改后：卡片**就地展开**（行内编辑），或属性栏内的轻面板；提交贴着字段。弹窗只保留离开兜底。

**流程 4：画面类配置（复用母版，不重设计）**

完全沿用：底栏 / 组内卡片 = 管理（列表 / 删除 / 总闸 / 回读）；画布 = 操作（框选 / 拖拽 / 提交 / 撤销）；浮条有变更才出现。

**流程 5：草稿保护（治 B10）**

现状只有 `requestClose`（关窗）一处拦截。改后：**把「会销毁草稿的动作」全部纳入** —— 切任务分组 / 切通道 / 关窗 / 页签离开。统一走同一句文案模板（母版 §11.2 第 3 层已给出）。

### 4.5 状态语言统一

把 §2.1-D 的十几套归并成**三层词汇**，全页复用：

| 层 | 回答的问题 | 视觉 | 词汇 |
| --- | --- | --- | --- |
| **事实层** | 设备现在是什么 | 实心 / 绿点 / 灰点 | 尚未读取 · 读取中 · 已同步（回读于 HH:MM） · 设备未返回此项 · 设备不支持 |
| **草稿层** | 我改了什么、还没生效 | **虚线 + 半透明 + 角标** | 待下发（N 项） · 已还原 |
| **结果层** | 发出去之后怎么样了 | 黄点 / 红点 / 灰点 | 已下发待回读 · 已接受但值未生效（mismatch） · 未应答（timeout） · 失败（附业务消息） |

规则：

- **三层不得混用视觉**：草稿层**永远**是虚线 + 半透明，不允许在某处用实心表示草稿（现状里看守位、扫描、巡航各有自己的表达）。
- **不新造词**：所有状态词必须能对应到后端 reconcile 的取值（母版 §4.5 已建立这套映射，直接升格为全页词表）。
- **⛔ 一律不出现传输层文案**（`Request failed with status code 400`）。
- 「指令已发出」与「设备已完成」在词汇上必须不同 —— 现状 `.cruise-running-chip` 已经做对（L5039 的 title 写「指令已发出」而非「运行中」），**把这条从特例提升为规则**。

### 9.1 第一步：视频编码并回画面设置（2026-09-20）

§4.1 的终态是「配置 = 1 个入口 + 组导航覆盖 7 组」（见 §7 Q3）。这一步只走了其中一段 ——
**把「视频编码」这个并列的一级页签收进「画面设置」**，一级页签从 5 降到 4：

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 一级页签 | 云台控制 · **画面设置** · **视频编码** · 设备维护 · 视频探针 | 云台控制 · **画面设置** · 设备维护 · 视频探针 |
| 画面设置侧栏 | 一个抽屉挂 `osd` 一组（`dcg-nav` 因单组而不渲染） | 一个抽屉挂 `video-param` + `osd` 两组，抽屉内二级导航等分切换，**默认落视频编码** |
| 画面设置底栏 | 遮挡 / 镜像 / **空位**（第三格 2026-09-19 起空着） | 遮挡 / 镜像 / **参数对照**（原视频编码页签的底栏块整块搬来） |

判据（用户视角）：视频编码、图像叠加、画面镜像、隐私遮挡改的是**同一台设备的同一路画面**；
分成两个并列的顶级入口之后，用户想"把画面调一下"得先猜进哪一个。
顺带把参数对照卡填进那个从 2026-09-19 起就空着的第三格 —— 它本来就该跟正在编辑的编码参数同屏。

三条随之而来的硬约束（都已在代码与用例里钉住，别松开）：

1. **底栏「码流」与侧栏「配置文件」必须是同一路** —— 真源只有一个（`selectedVideoStream`），
   抽屉的 `streamProfile` 是**受控** prop（`v-model:stream-profile`）。两个下拉各持一份状态，
   就会出现"对照卡说子码流、侧栏在改主码流"，而两边都不报错。
2. **切离「图像叠加」组必须退出 OSD 编辑模式** —— 编辑模式挂在画布那层锚点上；切到视频编码后
   锚点无处可拖，浮条上的「下发」也不含编码参数（`applyPictureAndOsdGroups` 只发画面 + OSD）。
   宿主因此持有 `activeGroupKey`（`v-model:active-group-key`）并监听它。
3. **对照卡上不再有读取 / 还原 / 下发** —— 侧栏抽屉的参数头已经有同一排（`dcg-embedded-actions`），
   同一屏两套同名按钮是本仓点过名的坑。

⛔ **未做**：§4.1 的"配置收成 1 个入口"还差「设备维护 → 基础参数」这最后一步；
Q1 / Q2（工作坞形态、遮挡与镜像归位到 `picture` 组）仍未拍板，别顺手改掉现有的底栏卡片。

### 9.2 第二步：一页全展示，底栏四格（2026-09-20 下午）

| 位置 | §9.1（已废） | 现在 |

底栏几何（实测，别按弹窗全宽算）：控制台主体是 `136px | minmax(0,1fr) | 360px`，
弹窗宽 `min(1520px, 100vw - 32px)` ⇒ **底栏可用宽只有约 940px**。四格按
`1.9fr / 1fr / 0.7fr / 1.05fr` 分 ⇒ 图像叠加 ~372 / 遮挡 ~196 / 镜像 ~137 / 对照 ~205。
正因为遮挡只剩 ~196px、镜像只剩 ~137px：遮挡由 2×2 改**单列**（2×2 每格 ~90px 会把坐标
`0,0,704,576` 截断），镜像单选 padding/gap 各收 1~2px。

新增/变更的硬约束（都已钉进代码与用例）：

1. **同一份 `familyValues.osd` 只能有一个编辑面** —— 图像叠加整块搬到宿主渲染后，
   抽屉侧 `osdBlocks` 袋 + `setOsdFlag` / `setOsdItems` 是唯一数据通路；宿主的
   `DeviceConfigOsdBlocks` 不再自持状态。§9.1 引入的 `v-model:active-group-key`
   随"两组切换"一起**删除**（`deviceconfig` 只剩一组，没有读方就不留口）。
2. **底栏 OSD 面板的禁用态必须按 `osd` 组算** —— 不能沿用 `familyFieldsDisabled`：
   它读 `activeGroup`（抽屉当前分组），而抽屉此刻常驻 `video-param`，
   `activeGroupFactsMissing` 在 `activeIsVideo` 时直接返回 false ⇒ 设备没回 `OSDConfig`
   时底栏控件反而可编辑，等于把平台空白模板（`timeX=10` 这类）当设备现状让人盲写。
   改用现成的 `osdEditable`（按 osd 组自身算）。
3. **嵌入且只剩一组时，参数区标题用 `navLabel`**（`activeGroupTitle`）——
   `dcg-nav` 只在 `configGroups.length > 1` 时渲染，导航一消失，`navLabel`（「视频编码」）
   就没别处可显示，只剩协议学名「视频参数属性」；`title` 属性仍挂标准全名，非嵌入照旧 `label`。
4. **对照卡做判定但不比码率** —— 判据是编码格式 / 分辨率 / 帧率三项；码率是**瞬时采样**
   （2 秒轮询），与"设备当前档位"不是同一个量，比它必然报假警报。分辨率按像素比、容差 ±20px
   （`D1 = 720×576` 与实测 `704×576` 属同档）；读不到写「未读取」而不是「不一致」。
5. **成对行的 CSS 选择器必须带 `.is-pair` 写成两条**（含 `.dcg-window--embedded .dcg-row` 那条），
   否则被嵌入态那条按顺序盖掉，表现为"合并了但看着还是两行"。
