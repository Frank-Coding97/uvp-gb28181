02五个必须先知道的事实

① CI 根本就没在跑 —— 不是"红了"，是"关着"

GitHub Actions 对该工作流返回的注册状态是 disabled_manually，最后一次运行时间戳是 2026-08-10。 也就是说仓库里 .github/workflows/ci-deploy-test.yml（2026-09-14 才改成现在的"只构建 + 只测后端"版本）从未真正执行过一次。

证据：curl -s https://api.github.com/repos/Frank-Coding97/uvp-gb28181/actions/workflows → "path": ".github/workflows/ci-deploy-test.yml", "state": "disabled_manually"；.../actions/runs 最新一条 created_at: 2026-08-10T12:58:54Z。

② 就算把 CI 打开，后端也会立刻红 —— 自研日志门禁已失守

仓库自建了一套日志契约门禁（internal/loggingcontract + internal/loggingcatalog），并且它是 普通 go test，会被 CI 的 go test ./... 命中。实测在干净的 HEAD 上就是失败。

HEAD 门禁 15 条：field_not_in_dictionary ×7、unregistered_event ×4、missing_event ×2、dynamic_message ×1、field_name_not_snake_case ×1
工作区（含 601 项未提交改动）门禁 54 条：contract 36 + catalog 18 —— 新代码让情况恶化了 3.6 倍

复现：cd server && go test ./internal/loggingcontract/ ./internal/loggingcatalog/（约 25s）。典型违规：app/gb28181/handler/register.go:304 使用了未注册字段 x_gb_ver / warning_code，并抛了未登记事件 gb28181.register.version_header_abnormal；app/gb28181/device/link_watch.go:126 的日志消息不是编译期常量。

③ 前端提交门禁是"写了配置但没接电"

✅ 已修（3b569e6f） —— 并查明了原先装不上的真正原因：husky 9 的安装逻辑要求执行时 cwd 下有 .git，而前端工程在 web/ 子目录，所以 prepare: "husky" 每次 npm install 都静默失败（只打印 .git can't be found，退出码仍是 0）。.gitignore 的忽略只是第二层原因。修法：.husky/ 放仓库根、prepare 改 cd .. && husky、钩子内 cd web 后再跑 lint-staged（husky 注入的 node_modules/.bin 是相对仓库根的，够不到 web/）。

以下为修复前的原始记录：

项目配了 commitlint、lint-staged、prettier、stylelint —— 但 package.json 里的 "prepare": "husky" 从来没生效过：仓库里没有 web/.husky/，git config core.hooksPath 为空，而 web/.gitignore 最后一段主动把 .husky/ 忽略了。

更直接的证据：web/lint-staged.config.cjs 第 3 行的命令写着 prettier --write--parser json —— 少一个空格，命令是坏的，一旦真接上钩子会立刻报错。

复现：git config core.hooksPath（空）、ls web/.husky（不存在）、grep husky web/.gitignore → .husky/。

④ 前端 230 个测试文件从未进过流水线，且现有 1 个用例是红的

web/package.json 有 test:unit: vitest，但 CI 里没有任何一步跑它（只有 build:prod）。本地全量跑：230 个文件、1536 个用例、1535 通过、1 失败。

勘误（2026-09-18 复核实测）

本报告「后端编译与格式」一行（原评 A）与「格式化零债务」这一条是错的，现更正为：
